---
title: "Release sgl-deep-ep Wheels"
description: "Build and publish the sgl-deep-ep CUDA 12.9 and CUDA 13.0 wheel matrices to PyPI and the SGLang wheel index."
---

Use the `Release sgl-deep-ep` GitHub Actions workflow to build platform wheels from the SGLang DeepEP fork. The workflow publishes CUDA 12.9 and CUDA 13.0 wheels to `sgl-project/whl` and publishes CUDA 13.0 wheels to PyPI.

## Understand the repository ownership

The release pipeline spans three repositories:

| Repository | Responsibility |
| --- | --- |
| `sgl-project/DeepEP` | DeepEP CUDA source branches and the shared `sgl_deep_ep` packaging overlay |
| `sgl-project/sglang` | Release workflow, Docker build environment, matrix orchestration, and wheel-index generation |
| `sgl-project/whl` | GitHub release assets and PEP 503 indexes under `cu129` and `cu130` |

The `sgl_deep_ep` packaging overlay exists only on the `sgl-deepep-x86` branch. The workflow checks out this overlay separately from the target DeepEP source branch. Do not copy the overlay into the ARM branches.

## Review the wheel matrix

The workflow builds 12 wheels for each release:

| CUDA | Python versions | Architectures | DeepEP source branch |
| --- | --- | --- | --- |
| 12.9 | 3.10, 3.12 | `x86_64` | `sgl-deepep-x86` |
| 12.9 | 3.10, 3.12 | `aarch64` | `sgl-deepep-cu12-arm` |
| 13.0 | 3.10, 3.11, 3.12, 3.13 | `x86_64` | `sgl-deepep-x86` |
| 13.0 | 3.10, 3.11, 3.12, 3.13 | `aarch64` | `sgl-deepep-arm` |

All wheels are compiled against PyTorch 2.11.0 with the following CUDA architecture list:

```bash
TORCH_CUDA_ARCH_LIST='9.0;10.0;10.3'
```

CUDA 12.9 wheels use a local version such as `0.1.0+cu129`. CUDA 13.0 produces two representations of the same compiled wheel:

- `0.1.0+cu130` for the SGLang wheel index.
- `0.1.0` for PyPI, where local CUDA version identifiers are not used.

## Configure release credentials

Configure these GitHub Actions secrets in `sgl-project/sglang` before publishing:

| Secret | Purpose |
| --- | --- |
| `SGL_DEEP_EP_PYPI_TOKEN` | Upload CUDA 13.0 wheels to the `sgl-deep-ep` PyPI project |
| `GH_PAT_FOR_WHL_RELEASE` | Create release assets and update indexes in `sgl-project/whl` |

Create the PyPI token with the narrowest available scope. For the first upload, use an account-scoped token that can create the `sgl-deep-ep` project. After the project exists, replace it with a project-scoped token. Store only the token value in `SGL_DEEP_EP_PYPI_TOKEN`; the workflow supplies the `__token__` username.

The `GH_PAT_FOR_WHL_RELEASE` token needs permission to create releases and push to the default branch of `sgl-project/whl`.

<Note>
PyPI Trusted Publishing should replace the long-lived token after the initial pipeline is operational. Configure the publisher for `sgl-project/sglang`, `.github/workflows/release-whl-deepep.yml`, and a protected `pypi` GitHub environment, then give the publish job `id-token: write`.
</Note>

## Check PyPI storage limits

PyPI applies a default 100 MB per-file limit and a 10 GB per-project limit. Check every CUDA 13.0 artifact before the first release:

```bash
du -h dist-pypi/*.whl
```

If a wheel exceeds the per-file limit, upload a smaller development release first to create the project, then request a project-specific limit increase from PyPI. Do not start the production release until the required limit is active.

## Prepare the DeepEP packaging ref

Before triggering a release:

1. Merge the shared packaging overlay into `sgl-project/DeepEP` branch `sgl-deepep-x86`.
2. Confirm that `sgl_deep_ep/VERSION`, `pyproject.toml`, the prerequisite checks, and the staging build script are present.
3. Confirm that the three DeepEP source branches contain the intended source revisions.
4. Use a commit SHA as the workflow `packaging-ref` when you need a reproducible release. The default branch name is convenient for development releases but can move between jobs.

The workflow writes its `version` input into the checked-out overlay before building. Do not commit release-specific version changes to all DeepEP branches.

## Trigger the release workflow

Open **Actions > Release sgl-deep-ep > Run workflow** in `sgl-project/sglang` and provide:

| Input | Value |
| --- | --- |
| `version` | Public package version, for example `0.1.0` or `0.1.1rc0` |
| `target` | `all`, `cu129`, or `cu130` |
| `packaging-ref` | DeepEP ref containing the shared packaging overlay; defaults to `sgl-deepep-x86` |

You can also trigger it with the GitHub CLI:

```bash
gh workflow run release-whl-deepep.yml \
  --repo sgl-project/sglang \
  --ref main \
  -f version=0.1.0 \
  -f target=all \
  -f packaging-ref=sgl-deepep-x86
```

The workflow always publishes after the requested build matrices succeed. It does not have a build-only or dry-run input. Use a release-candidate version when validating publication behavior.

## Follow the workflow stages

The workflow executes these stages:

1. `build-cu129-matrix` builds four wheels on the x86 and ARM wheel-builder runners.
2. `build-cu130-matrix` builds eight wheels on the x86 and ARM wheel-builder runners.
3. Each build uses `docker/sgl-deep-ep.Dockerfile`, which installs the selected Python, CUDA-matched PyTorch, RDMA build dependencies, and the GDRCopy user-space library.
4. Each build uploads its wheel as a GitHub Actions artifact.
5. The wheel release job uploads CUDA-tagged artifacts to a single `sgl-project/whl` GitHub release and updates both requested PEP 503 indexes in one commit.
6. The PyPI release job uploads the eight CUDA 13.0 wheels without the `+cu130` local version.

The build container installs `libgdrapi` and its headers. It does not build or load the `gdrdrv` kernel module. The machine that imports and runs DeepEP must provide a compatible NVIDIA driver, `gdrdrv`, `/dev/gdrdrv`, and the required RDMA configuration.

## Verify published artifacts

After a CUDA 13.0 release, verify the default PyPI installation in clean environments for each supported Python minor and architecture:

```bash
python -m pip install --upgrade pip
python -m pip install "sgl-deep-ep==0.1.0"
python -c "import deep_ep; print(deep_ep.__file__)"
```

Verify the CUDA-tagged indexes with an exact version:

```bash
python -m pip install "torch==2.11.0" \
  --index-url https://download.pytorch.org/whl/cu129
python -m pip install "sgl-deep-ep==0.1.0+cu129" \
  --index-url https://docs.sglang.io/whl/cu129 \
  --extra-index-url https://pypi.org/simple
```

For CUDA 13.0 from the SGLang index, replace `cu129` with `cu130` in both commands and request `0.1.0+cu130`.

Confirm that the project pages contain the expected artifacts:

- `https://pypi.org/project/sgl-deep-ep/`
- `https://docs.sglang.io/whl/cu129/sgl-deep-ep/`
- `https://docs.sglang.io/whl/cu130/sgl-deep-ep/`
- `https://github.com/sgl-project/whl/releases/tag/v0.1.0`

## Recover from a partial release

PyPI artifacts are immutable. Do not rebuild different binaries and upload them under an already published version. If only part of the CUDA 13.0 matrix reaches PyPI, rerun with identical source and packaging commits so existing files can be skipped safely. If any source, dependency, or compiler input changes, increment the package version.

If the GitHub release succeeds but an index update fails, regenerate the index from the existing release assets and push the index change without rebuilding the wheels. Yanking a PyPI release does not delete its files or free project storage.
