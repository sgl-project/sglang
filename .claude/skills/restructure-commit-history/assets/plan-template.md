# <项目/分支> 提交历史重构计划（<版本>：<N> → <M> 提交）

> 状态：**纯计划文档，未执行任何 Git 操作、未修改任何代码。**
> 范围：`HEAD~<N>..HEAD`（<首hash> … <尾hash>），基线 `<baseline>`。
> 目标：消除"先破坏后修复"痕迹、合并零散重复修改、（可选）拆分多主题混合提交。
> 树内容约束：重构后 `git diff <旧HEAD> <新HEAD>` 必须为**空**（可选项须显式声明并经用户同意）。

## 2. fix→origin 折叠（F1–F<n>）

原则：fix 提交的内容并入引入该缺陷的原始提交，历史中不再出现"引入缺陷 →
若干提交后修复"的痕迹。所有折叠对均已核查"origin 与 fix 之间无第三方提交
触碰同一文件同一区域"，预期零冲突或仅上下文微调。

### F1 `<fix-hash>` → `<origin-hash>`（<一句话缺陷名>）
<缺陷机理：origin 为什么引入了缺陷（社区重构背景 / 移植盲区等）；
fix 如何补救；两者之间该文件的第三方触碰情况（应为零或区域不重叠）。>

## 6. 执行手册

### 6.1 安全网（前置，均不改变分支内容）

```bash
git branch backup-restructure-<N> HEAD    # 冻结现状
git config rerere.enabled true           # 冲突解法复用
```

### 6.2 分阶段（低风险 → 高风险）

- **阶段 1 — 整提交折叠（fixup 重排）**：F… 列表；均已验证零干扰
- **阶段 2 — 分发折叠**：F… / F<n> 拆份；edit 停靠 + `git apply --3way --index`
- **阶段 3 — 消息重写**：M 组基提交逐个 amend（Why/How/Dependency/Test 合并）
- **阶段 4 — 高风险组最后**：M<k>（降级方案见 §4）

### 6.3 rebase todo 骨架（示意，仅列非普通 pick 行）

```
pick <hash> …
# <hash> —— 删除（互逆对之一）
edit <origin>   # 吸收 F<n>（<fix> 的 <文件> hunk）
pick …
fixup <fix>     # F<n> 整提交折叠（行已移至 origin 之后）
# 以下提交行在 todo 中删除（内容已吸收）：
#   <被吸收 fix hash 列表>
```

### 6.4 冲突热点预警（按风险排序）

1. **M<k>**（N 合一前移）：<文件/区域> 上下文漂移来源与预期解法
2. **F<n><份>**：<插入点/依赖漂移> 说明
3. 其余折叠均为零间隔冲突

### 6.5 完成校验（必须全过）

```bash
git diff backup-restructure-<N> HEAD        # 期望：空
git rev-parse "HEAD^{tree}" "backup-restructure-<N>^{tree}"   # 期望：相同
git rev-list --count <baseline>..HEAD       # 期望：基线提交数 + <M 口径修正>
git range-diff <baseline> backup-restructure-<N> HEAD
pre-commit run --all-files                  # 树一致性验证之后单独跑
python -m pytest <单测抽查目录> -q
```

### 6.6 提交信息规范

- 合并/折叠后的提交按 `.claude/skills/patch-refinement/assets/commit-message-template.txt`
  （Why/How/Dependency/Test）改写 message，正文吸收被折叠提交的 Test 段。
- 保留原 `(cherry picked from ...)` trailer；rebase 保留原作者署名
  （squash 以基提交作者为准，其余贡献者以 `Co-authored-by:` 补充）。
- amend 一律 `--no-verify`（pre-commit hooks 可能改文件，破坏树一致性）。

### 6.7 明确不做的事

- 不做全局主题重排（§5 已按"原时序为骨架"设计）。
- 不改任何代码逻辑；最终树与现 HEAD 逐字节一致（可选项须显式声明）。
