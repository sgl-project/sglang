# 第 3 章 服务端是一座分工明确的餐厅

> 本章不贴代码，只讲"心智模型"。这是全书最重要的一章——后面所有章节都是在给这张图补细节，请反复回看。

## 3.1 五个角色

把 SGLang 服务想象成一家餐厅，一次请求就是一位顾客点菜：

| 餐厅 | SGLang | 干什么 |
| --- | --- | --- |
| 前台 | HTTP 层 | 接单：收下顾客的点单（请求），把做好的菜端出去（响应） |
| 点单员 | TokenizerManager | 把口头点单翻译成标准单据：文本 → token id；出菜时再把单据翻译回菜名：token → 文本 |
| 后厨调度台 | Scheduler | 决定先做哪桌的菜、每轮做多少，是整个餐厅的"大脑" |
| 灶台 | GPU + 模型 | 真正做菜：一次前向计算 |
| 出餐口 | Detokenizer | 把灶台端出来的"半成品"拼装成完整的菜（避免逐 token 拼出乱码） |

一条请求的旅程：

```text
顾客 → 前台接单 → 点单员翻译成单据 → 后厨调度台排期
     → 灶台做菜（prefill 备料 + decode 逐道出） → 出餐口拼装 → 前台端菜上桌
```

## 3.2 为什么要分成"几个角色"而不是一个人干完

一个很自然的疑问：为什么不能一个进程从头干到尾？

答案藏在"后厨忙的时候，前台不能停"里。如果前台、调度、灶台全挤在一个进程里，灶台在算的时候（可能几百毫秒），前台就被堵住没法接新单。拆开之后：

- 灶台专心算，算完一桌就把结果交给出餐口，立刻接下一桌；
- 前台专心接单，永远不阻塞；
- 调度台在后厨"等菜"的间隙，就已经把下一批菜单排好了。

这就是 SGLang 服务端**多进程架构**的原因，也解释了为什么吞吐高：**每个角色各干各的，谁都不等谁。**

## 3.3 排队：等位的和正在做的

餐厅里有两拨顾客：

- **等位的**：刚点完单、还没轮到做 → 对应调度器里的 **waiting queue**（等待队列）；
- **正在吃的**：菜已经在上，随时可能加菜或吃完走人 → 对应 **running batch**（运行中的一批请求）。

调度台每隔一小会儿做一次决策（这就是"调度循环"）：

1. 看看有没有新点单进来 → 放进等位区；
2. 从等位区里挑一些，凑成一桌大桌（**组 batch**）→ 交给灶台一次做；
3. 灶台做完这一轮，看看哪些桌吃完了 → 送客（请求完成），空出的位置让等位的补上。

这就是第 1 章说的**连续批处理**在系统里的落地：一批请求不是"同生共死"，而是有人走有人来。

## 3.4 半成品冷柜：KV Cache 和它的前缀复用

灶台有个冷柜（**KV Cache**），里面存着"做了一半的菜"（每层算好的 Key/Value）。

两个顾客都点了"宫保鸡丁 + 米饭"（相同的前缀 prompt），第二桌的配菜就不用重新备了——直接从冷柜里拿第一桌的。冷柜够聪明的话，任何重叠的前缀都能共享。

冷柜的规则：

- **放什么**：一桌菜做完，如果冷柜还有空，就把这份半成品放进去（请求结束 → KV 写回缓存）；
- **怎么找**：按"前缀"匹配，最长匹配优先（这就是 LPM 调度策略的由来）；
- **放不下怎么办**：把最不常用的半成品扔了（缓存淘汰，LRU 之类）；
- **卫生隔离**：加了 LoRA 适配器的菜，不能和普通菜共享半成品（这就是"前缀命名空间隔离"的直觉版本）。

## 3.5 一个请求的生命周期（餐厅版）

把第 2 章那个 curl 请求完整走一遍：

```text
1. 你 curl → 前台接单
2. 点单员把"用一句话介绍你自己"翻译成 12 个 token
3. 单据送到调度台 → 进等位区
4. 下一轮调度：这桌被选中 → 灶台做 prefill（处理 12 个 token，备好 KV 半成品）
5. 出餐口把第一个 token 拼成第一个字，前台先端上来（流式：TTFT = 这一刻）
6. 灶台一轮一轮 decode，每轮 1 个 token；出餐口拼装成词、成句
7. 碰到结束符或达到 max_tokens → 这桌吃完，结账（返回 usage 统计）
8. 半成品（KV）放进冷柜，等位区下一桌补上
```

两个新词在此登场，后面会一直用：

- **TTFT**：从发请求到收到第一个 token 的时间。主要取决于第 4 步 prefill 多快。
- **TPOT**：相邻两个 token 的间隔。主要取决于第 6 步 decode 多快。

## 3.6 三个"先记住再深究"的结论

1. **服务端是多个角色分工的**，前端和灶台之间靠"单据"（消息）传递，单据就是一个叫 `GenerateReqInput` 的对象——名字可以后面再记。
2. **调度是轮询式的**：调度台每隔一小段时间就做一次"收单、组批、下灶"的循环。这个循环的代码就是后面第 7 章的绝对主角。
3. **KV 半成品可以跨请求复用**，这是 SGLang 区别于很多框架的招牌能力。
