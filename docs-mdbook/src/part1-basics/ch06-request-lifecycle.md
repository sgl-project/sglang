# 第 6 章 一次请求的完整旅程（入门版）

> 这是入门部分的"总复习"：把前 5 章的知识串成一条完整的链路。看完这一章，你应该能给别人讲清楚"从 curl 到返回，中间发生了什么"。

## 6.1 旅程全景

还是那个 curl 聊天请求。这次我们对照着第 3 章的餐厅角色，把每一步标出来：

```text
你 (curl)
  │ ① HTTP 请求
  ▼
前台（HTTP 层）────────────── 接单，解析 JSON，校验参数
  │ ② 把"messages + sampling"打包成内部请求对象
  ▼
点单员（TokenizerManager）─── ③ 文本 → token ids（12 个）
  │                          └ 顺便做：多模态预处理、LoRA 解析、会话状态
  │ ④ 单据通过内部消息通道送给后厨
  ▼
后厨调度台（Scheduler）────── ⑤ 放进等位区 → 下一轮调度被选中
  │                          └ 检查显存、组 batch、决定 chunk
  ▼
灶台（GPU + 模型）─────────── ⑥ prefill（算整段 prompt，写 KV Cache）
  │                          └ 之后每轮 decode（每轮 1 个 token）
  ▼
出餐口（Detokenizer）──────── ⑦ token → 文本（增量拼装，不出乱码）
  │ ⑧ 结果通过消息通道送回
  ▼
前台（HTTP 层）────────────── ⑨ 组装成 SSE 或完整 JSON，端回给你
```

如果去掉所有比喻，用系统的语言就是：

```text
HTTP 请求 → 协议解析 → TokenizerManager（tokenize）
→ 调度器（排队 + 组批 + 显存管理）→ ModelRunner（GPU 前向）
→ Detokenizer（detokenize）→ HTTP 响应
```

**把这条链路刻进脑子里**，后面所有章节都是它的局部放大。

## 6.2 放大看几个容易忽略的点

### 一个请求 ≠ 一次 GPU 前向

一次 curl 请求要触发**很多轮** GPU 前向：1 轮 prefill + N 轮 decode（N = 输出 token 数）。所以请求日志里你会看到 1 次 prefill 后面跟着一串 decode。

### 请求在调度器里"等"了很久

从 ④ 到 ⑤，请求可能排队一小会儿——调度器不是立刻处理，而是**周期性**地"收一批、做一批"。排队时间就是 TTFT 的一部分。

### 流式时，链路是"边做边回"的

流式不是"全部做完再返回"，而是第 6 步每 decode 出一个 token，就走一遍 ⑦⑧⑨，把增量推给你。所以你会看到文字一段一段出现。

### 批处理请求是"并成一条队"的

如果你一次发 100 条 prompt（`generate` 传列表），前端会拆成 100 个内部请求，但它们会**一起排队、一起被组进 batch、共享 GPU 前向**。

## 6.3 一条链路，三种"单据"

链路里流转的消息对象值得混个脸熟（现在只需要知道"有这回事"，不用记路径）：

| 阶段 | 单据内容 | 什么时候出现 |
| --- | --- | --- |
| 前台 → 点单员 | 文本、采样参数、图片等（`GenerateReqInput`） | 请求刚进来 |
| 点单员 → 调度台 | token ids、采样参数、KV 预算需求（`BatchTokenizedGenerateReqInput`） | 分词之后 |
| 调度台 → 前台 | 新 token、文本增量、统计信息 | 每一轮之后 |
