What triggers AMD CI

Three gates, all of which must pass before a single GPU job starts. The first and third are path checks that use different syntax and different path lists, which is where the coverage holes come from.

Gate 1 — the run is created

on.pull_request.paths. No types is declared, so only opened, synchronize and reopened fire — adding the run-ci label or marking a draft ready does not dispatch a run. There is no branches restriction.

Path patternEffect
python/**Any Python change, including files no AMD filter later matches.
scripts/ci/**All CI scripts, not just the AMD ones.
test/**The whole test tree.
python/sglang/kernels/aot/**AOT kernel sources.
.github/workflows/pr-test-amd-rocm720.ymlThe workflow editing itself.
docker/rocm.DockerfileCreates a run, but matches no filter — see the gap below.

Gate 2 — pr-gate.yml

Called with all defaults and evaluated at job runtime against a live API read, so a rerun picks up the current state. The PR must not be a draft and must carry the run-ci label. Actors without write access get a 120-minute cooldown — computed from pr-test.yml run history, so the cooldown is shared with CUDA CI.

The gap between gate 1 and gate 3
Gate 1 admits scripts/ci/** and docker/rocm.Dockerfile, but gate 3 only matches scripts/ci/amd/* and scripts/ci/utils/* — both single-level — and never matches the Dockerfile at all. Anything in that gap creates a run in which every job skips, and since nothing fails, the run reports green. Eleven PRs landed that way this week, including a ROCm Dockerfile change and a python/pyproject.toml bump. Also caught: scripts/ci/cuda/, scripts/ci/npu/, scripts/ci/xpu/, scripts/ci/slurm/**, scripts/ci/utils/diffusion/** and scripts/ci/runner_configs.yml.

Where the week’s merges landed

measured on each PR’s merge commit
OutcomePRsShareWhat it means

Of the 346 PRs that should have run AMD GPU jobs, 273 reached a GPU but only 77 produced a complete verdict before merging — and 73 of those 77 were red. Put the other way: 95% of finished AMD runs this week were failing, and the remaining 269 eligible PRs merged with no AMD answer at all.

The dominant failure mode is timing, not labels

Cancellation, not the run-ci gate, is what removes most AMD signal. Of the 196 cancelled runs, 190 (97%) were killed at or after the merge, a median of one minute afterwards — that is cancel-pr-workflows-on-close.yml reacting to pull_request_target: closed. When killed, a median of only 25% of their GPU jobs had passed.

The loop
Queues run hours deep, so a run finishes long after its PR is ready. The PR merges, the run is cancelled, and the capacity spent on it is wasted — which lengthens the queue for the next run. Adding runners alone does not break this; shortening the wall-clock time of a run until it beats the merge does.

The binding constraint is linux-mi35x-gpu-8.fabric: one runner, one disaggregation job per main_package PR, a 60-minute timeout. It can serve at most about a dozen runs a day against a demand of roughly 40. Worst observed wait was 660 minutes. The max-parallel throttles compound this — the 14-way stage-b matrix is capped at 4, and several other stages at 1 — which converts a wide run into a long one, and long runs are exactly what the merge cancels.

#34812 — gate AMD tests on rocm.Dockerfileverified live

Adds docker/rocm.Dockerfile to main_package and removes a dead python/pyproject_rocm.toml rule. The pins in that file are not inert: amd_ci_install_dependency.sh greps AITER_COMMIT_DEFAULT and MORI_COMMIT at job time and rebuilds against them, because the image is never rebuilt for a PR.

Nine commits in 60 days touched only this file. One of them, a MoRI bump, reported a green AMD check with all 17 GPU jobs skipped.

#34813 — show AMD state in the PR bodyverified live

pr-states.yml writes a CI-states block into every PR description but only queries pr-test.yml and pr-test-extra.yml. A merge oncall reading the description cannot see AMD at all. Adds a third row plus a notify-pr-states job so reruns refresh it.

Costs no runner capacity. The rendering cannot be tested by a PR run, since pull_request_target always executes the base-branch copy.

Not yet addressed

Both open PRs together cover the 11 skipped-everything PRs and the 71 gate-blocked ones. They do nothing for the 196 cancelled runs, which is the largest bucket. That one needs the run to get shorter than the time-to-merge: move the disaggregation and DeepSeek-V4 accuracy jobs off the per-PR path onto nightly or the existing run-ci-extra opt-in, which frees the single fabric runner and five of the seven MI35x 8-GPU slots per run, then relax the max-parallel caps so the remaining suite runs wide instead of long.

Method. 423 PRs merged into sgl-project/sglang between 2026-08-07 and 2026-08-14 18:39 UTC, joined against the GitHub Actions API by merge-commit SHA.
