## 3. 关键洞察:LRU 在 agent 负载下方向反了(论文核心论点)

经典缓存 LRU 假设"最近用过 = 马上再用"。agent 会话恰好相反:
**刚结束 action turn = 正在等待外部工具 = 还要隔 gap_s 才回来**,而且 gap
由工具延迟分布决定(**可预测**——这是与经典缓存负载的本质区别)。

- LRU 优先驱逐 last_access_time 最小的 = **离返回最近的会话** → 快工具会话
  被反复驱逐重算(thrashing),慢工具(run_tests)会话反而多活很久
- 最优(Belady 式,gap 可知)= 驱逐 expected_next_access 最远的 = **刚开始长工具等待的会话**
- v0 策略:`evict_key = −(last_access_time + E[gap|tool])`;工具身份从输出文本的
  `<tool_call>` token 序列识别(scheduler 侧,无需 IPC);`E[gap|tool]` 支持在线
  EMA 学习(会话返回时 elapsed 可观测)

### 核心发现:三区模型(论文骨架)

1. **可容纳区(超卖 <1×)**:fp4 N=32 时 200k 活跃集装进 280k 池 →
   bf16 同负载 miss 81%→**17.7%**,TTFT p50 **15s→303ms(50×)**——
   **容量本身就是最大的 Agent 提速手段**;残余 miss 来自 gap 期 churn + 分类噪声
2. **边际区(1×~1.4×)**:排序决定谁幸存 → Score 稳定赢
   (bf16 N=16:-23% miss;fp4 N=32:-24% miss/-31% 浪费;quick-tool miss→0)
3. **深饱和区(>1.4×)**:容量硬顶,任何排序无效,clamp 保护反而挤占容量
   (Score 反超 LRU)→ 需要**压力感知自适应降级**(future work:miss 率反馈
   或队列深度触发回退 LRU)

工程含义:MXFP4 与 Score 驱逐是**互补而非竞争**——量化把工作负载从崩溃区搬进
可容纳/边际区,排序在边际区优化剩余冲突。 sustainable concurrency 包络:
bf16 ≈ 40 路(13.5% miss)→ fp4+Score ≈ 120+ 路(同 miss 水平),~3×。

### 诚实声明(论文里要写的)

- 深饱和区 Score 劣于 LRU 是当前实现的真实缺陷(保护失效机制已定位,
  自适应降级未实现)
- fp4 组 miss 分类器在深队列下有偏差,绝对值偏低估驱逐
- seed 单次;seed=8 重复在跑
