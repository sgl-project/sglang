## Choose a prefill backend

SGLang supports `breakable`, `full`, and `disabled` for the prefill phase.
Breakable CUDA graphs (BCG) are the default on CUDA for compatible configurations.
Other platforms keep prefill graphs disabled by default; support depends on the platform and model.

BCG captures the transformer body as CUDA graph segments separated by eager regions.
At replay, attention and other eager regions receive the current prepared batch.
Inputs use captured token-size buckets, while the outer model tail runs with live request metadata.

The `full` backend captures the transformer body in one graph with a fixed request-slot capacity.
Batches exceeding that capacity fall back to eager execution.

The former `tc_piecewise` backend and its `tc_compiler` option have been removed.
Its implementation remains as inactive source under `reference/tc_piecewise` for historical reference.
`--enable-torch-compile` and the decode compilation helpers remain available independently.

## Configure capture

For a supported model on Linux with NVIDIA CUDA, choose BCG explicitly:

```bash
python3 -m sglang.launch_server \
    --model-path MODEL_PATH \
    --cuda-graph-backend-prefill breakable
```

Use `--cuda-graph-backend-prefill disabled` to disable prefill graphs.
Use `--cuda-graph-bs-prefill 64 128 256 512` to specify token buckets, or
`--cuda-graph-max-bs-prefill 2048` to set the maximum captured token count.

Both phases can be configured together:

```bash
python3 -m sglang.launch_server \
    --model-path MODEL_PATH \
    --cuda-graph-config '{"decode":{"backend":"full"},"prefill":{"backend":"breakable","bs":[64,128,256,512]}}'
```

For full prefill capture, select `full` and set
`prefill.full_prefill_max_req` in `--cuda-graph-config` to control captured request slots. See the
[server arguments](/docs/advanced_features/server_arguments) for the supported configuration fields.

## Mark eager regions

Use a method on the owning layer with `@eager_on_graph`:

```python
@eager_on_graph
def _eager_attention(self, query, forward_batch):
    return self.run_attention(query, forward_batch)
```

Outside breakable capture, the method runs normally. During capture, the decorator
ends the current segment, executes the method, and starts the next segment.
During replay, its named `forward_batch` argument is rebound to the current prepared batch.
Other arguments retain their capture-time identity, so tensor inputs must refer to
static buffers refreshed by the runner. Eager output tensors retain stable addresses.

Use `@eager_on_graph(capture_stub=...)` only when capture needs an output-allocation stub;
replay still executes the real method. The stub has the same signature as the method.

## Troubleshooting

If capture runs out of memory, reduce the maximum token bucket or
`--mem-fraction-static`. To compare against eager execution, disable prefill graphs.
Explicitly selecting a backend skips some automatic compatibility gates; it does
not make an unsupported model or platform capture-safe.
