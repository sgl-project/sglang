Expert Parallelism (EP) in SGLang distributes expert weights across multiple devices in Mixture-of-Experts (MoE) models, addressing memory bottlenecks and enabling efficient scaling for high-performance inference. It is particularly vital for serving large-scale MoE models where tokens are dynamically routed to specialized experts across GPUs. By leveraging optimized all-to-all communication and grouped matrix multiplications (GEMMs), EP reduces latency, boosts throughput, and minimizes idle GPU time. SGLang's EP offers strong extensibility through its modular framework, allowing seamless integration of custom kernels, backends, and optimizations without refactoring core logic, supporting diverse hardware and quantization schemes.

## Supported Backends and Selection Guidance

SGLang's EP integrates diverse, highly efficient backends for different use cases, allowing fine-grained control over performance trade-offs. Users specify backends via command-line flags:
- `--moe-a2a-backend`: Selects the backend for all-to-all communication.
- `--moe-runner-backend`: Selects the backend for MoE computation.

DeepEP and Mooncake backends support two modes for token dispatch: `normal` mode (optimized for prefill workloads with high throughput) and `low_latency` mode (optimized for decode workloads with low latency and CUDA Graph compatibility). MORI backend only supports `normal` mode now. NIXL-EP and PPLX currently operate in low-latency mode with CUDA Graph support (PPLX reuses the DeepEP low-latency masked expert-compute path). Users are recommended to set `--deepep-mode auto` to enable automatic dispatch mode switching during runtime. Setting `--deepep-mode normal` or `--deepep-mode low_latency` is useful for debugging or development purposes.

Currently, DeepEP, Mooncake, NIXL-EP, `ascend_fuseep`, `pplx` and MORI only support cases where `ep_size = tp_size`. For hybrid EP and TP (i.e., `ep_size < tp_size`), only the `none` backend (All-Reduce or All-Gather-based dispatching) is supported. Note that `pplx` additionally requires DP attention with at least 2 attention DP groups (i.e., `--attn-dp-size` > 1, so `tp_size / attention_tp_size > 1`); otherwise pplx-kernels' AllToAll cannot be constructed.

## Extensible EP Framework

SGLang's EP framework provides modular abstractions for easy integration of custom kernels, backends, and optimizations. It decouples the MoE forward pass into stages (dispatch → pre-permute → core runner → post-permute → combine), enabling seamless extensions without refactoring core logic. A fused function registered for a layer's all-to-all and runner backends replaces the three middle stages.

### Framework Overview

The framework centers on `FusedMoE` as the unified entry point for a single, extensible structure. Key components include:
- **Dispatcher**: Manages dispatch/combine for backends like DeepEP (implements `BaseDispatcher` subclasses).
- **MoeRunner**: Orchestrates grouped-GEMM execution via `MoeRunnerCore` implementations (e.g., `TritonRunnerCore`).
- **FusedOpPool** and **PermuteMethodPool**: Auto-register fused functions per all-to-all and runner backend pair (`register_fused_func`) and layout conversions (`register_pre_permute` and `register_post_permute`). `MoeRunner.run` calls the fused function when one is registered for the layer's pair and LoRA is disabled; otherwise it runs pre-permute, the runner core, and post-permute, or hands the dispatch output to a `DispatchMoeRunnerCore`.
- **TopK Router**: Backend-agnostic expert selection.

This design supports multiple backends via `--moe-a2a-backend` and `--moe-runner-backend`, with quantization integrated through a standardized `apply()` method. The computation flow ensures modularity:

```text Output
[input_hidden_states]
          |
          v
     TopK.forward -> select_experts / bypass
          |
          v
     [TopKOutput]
          |
          v
   FusedMoE.forward -> Dispatcher.dispatch -> DeepEP / bypass
          |                     |
          |                     v
          |              [DispatchOutput]
          |                     |
          |                     v
          |             quant_method.apply -> MoeRunner.run
          |                     |              |
          |                     |              v
          |                     | fused func
          |                     | or DispatchMoeRunnerCore.run_from_dispatch
          |                     | or pre-permute + grouped_gemm + post-permute
          |                     |              |
          |                     |--------------
          |                     v
          |               [CombineInput]
          |                     |
          |                     v
          |            Dispatcher.combine -> DeepEP / bypass
          |                     |
          |---------------------
          v
[final_hidden_states]
```

For details, see the [MoE Refactor Roadmap](https://github.com/sgl-project/sglang/issues/8715).

### Implementing New Backends

To add a new backend:
1. For a new all-to-all dispatcher, implement a `BaseDispatcher` subclass with `dispatch` and `combine` methods.
2. For a new MoE runner backend, define a `MoeRunnerCore` subclass for core operations (e.g., grouped GEMMs).
3. Define new input/output formats for the dispatcher or model runner (e.g., `RunnerInput`, `RunnerOutput`).
4. Register permute/unpermute methods to ensure compatibility:
   - **Fused Mode** (static, torch.compile-compatible): Use `register_fused_func` for end-to-end operations.
   - **Permute Mode** (dynamic): Register `register_pre_permute` and `register_post_permute` for flexible layouts.

   When both are registered for a backend pair, the fused function takes precedence; the non-fused path still serves LoRA, which skips fused functions.

See the [MoE Refactor Implementation PR](https://github.com/sgl-project/sglang/pull/9269) for full changes, including type hints and config expansions.

### Examples

For an example implementation, see [moe_runner/triton.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/moe/moe_runner/triton.py), which demonstrates Triton-based grouped GEMMs with a fused function registered for the `none` all-to-all backend and permutation functions as the fallback path, used for example with LoRA.

## Computation and Communication Overlap

SGLang's EP employs advanced overlap techniques to hide communication latency behind computation, maximizing GPU utilization in MoE layers.

### Two-Batch Overlap (TBO)

TBO splits requests into micro-batches, interleaving attention computation with dispatch/combine operations. Yield points in the execution graph allow pausing for overlaps, increasing overall throughput without peak memory spikes:

```python Example
operations = [
    self._forward_attn,
    YieldOperation(),  # Overlap with dispatch of prior micro-batch
    self._forward_dispatch,
    self._forward_mlp,
    YieldOperation(),  # Overlap with combine
    self._forward_combine,
]
```

Users need to specify `--enable-two-batch-overlap` to unlock up to 2x throughput. For details, see the [Large-Scale EP Blog](https://lmsys.org/blog/2025-05-05-large-scale-ep/#two-batch-overlap).

### Single-Batch Overlap (SBO)

SGLang introduces a dispatcher-hook system for Single-Batch Overlap (SBO), enabling the overlap of operations within a single batch—such as shared experts computation with communication—while decentralizing logic to enhance modularity. These hooks execute before and after the `dispatch` and `combine` operations without modifying core MoE modules. This design simplifies interfaces, reduces coupling, and improves extensibility. For implementation details and an example of overlapping shared experts with DeepEP's combine operation, refer to [PR #13327](https://github.com/sgl-project/sglang/pull/13327). Users can set `--enable-single-batch-overlap` to enable this feature.


## Workload Balancer

SGLang integrates the [Expert Parallelism Load Balancer (EPLB)](https://github.com/deepseek-ai/EPLB) from DeepSeek to address routing imbalances in MoE models. By analyzing expert activation statistics, EPLB computes an optimal expert arrangement, strategically placing or replicating experts to minimize GPU utilization variance, reduce idle cycles, and enhance scalability.

Enable EPLB with `--enable-eplb`. By default the manager checks the placement every 1000 eligible target forwards. Each prefill or decode endpoint counts its own forwards. The recorder window defaults to the configured check interval.

### Choosing a check interval on Ascend

Add `--eplb-interval-policy recommend` to your existing EPLB launch to compare your current interval with shorter and longer alternatives. A worker serving both prefill and decode (the default `--disaggregation-mode null`) uses one layout and one check interval. It starts at 1000 forwards unless you set `--eplb-rebalance-num-iterations`. On separate prefill and decode workers, each endpoint chooses its own interval. The [Ascend 910C DeepSeek-V4-Flash EP16 profile](https://github.com/sgl-project/sglang/pull/49701) starts from interval/window 50/50 on prefill and 4000/1000 on decode. An explicit recorder window takes precedence and stays fixed during serving.

Experimental interval replay supports single-node, synchronous TP=EP, PP1 with static Ascend Ops, FuseEP or DeepEP dispatch, the exact `stat` recorder and the DeepSeek placement algorithm. Use the default rebalance threshold and full-model updates. Workers outside this scope log their fixed fallback. In recommend and auto deployments, reading or exporting statistics preserves the rolling window. Counts retain the logical expert IDs used when each step ran. A worker can check every 25 forwards using the last 50 forwards each time. It waits for 50 rows before its first check.

Query the endpoint directly. Each candidate fits a layout using only past rows. The controller then scores all candidates on the same subsequent forwards, sampling up to eight per block. The replay reports busiest-rank demand, peak share, checks and changed slots in two successive observation spans. For each span, `identical_layout_and_dispatch` is true only if the candidate and current interval used the same physical layout and every source rank selected the same replica throughout the span. This comparison covers the steps between installations, including forwards outside the load sample.

The controller discards a replay if the reference disagrees with the installed slots or dispatch table. One background CPU worker computes candidate-only layouts from a snapshot. The scheduler still gathers statistics and distributes finished layouts. If a plan is late, all ranks discard that observation and keep the current interval. Check `shadow_plan_deadlines_missed` in the endpoint state. A foreground wall-time budget pauses expensive replays. When available, the state reports the estimated extra check time per forward.

```bash
curl -fsS http://localhost:30000/server_info | jq '.internal_states[].eplb_interval'
```

Use `--eplb-interval-policy auto` to allow bounded live trials. The controller compares matching batch shapes across ranks and adds the mean measured check cost per forward, including occasional expensive migrations. For prefill and mixed batches, the match also accounts for how new tokens are divided among requests and their cached prefixes. It groups the average number of visible keys per new query in buckets of 128. Each trial runs for four complete periods, extended to at least 32 forwards for short intervals. All ranks sample the same jittered forward in each timing block. Retaining the interval requires at least 32 matched active timings, matching shapes and complete timings for at least 75% of all scheduled non-idle samples on each side, and more than 1% improvement in both the amortized mean and the amortized median. The controller restores the prior interval on insufficient coverage, insufficient gain, or a material forward P95 regression.

On a colocated worker, short trials run for at least 60 forwards. In `last_trial.by_phase`, inspect the matched timing coverage and device forward P95 for each phase seen in either window. Target verification counts as decode. A batch containing both prefill and decode, or a step where different active ranks serve different phases, counts once as mixed. Each observed phase needs at least 20 matched timings and 75% coverage on both sides. A phase P95 increase above 2% can veto a faster overall mean. A phase that disappears or has too few samples makes the trial inconclusive. The controller also restores the previous interval when the overlap between phase proportions (`phase_mix_overlap`) falls below 0.75. Only phases actually observed are compared. Runtime PD role switching still uses fixed checks.

Read `last_trial` for the two intervals, the decision, sampling coverage, and the check cost per forward. The baseline and trial timing coverage show scheduled steps, fully idle steps, complete active timings, and incomplete timings. In `last_trial`, `matched_fraction` reports the coverage used for the decision on each side. The `missing_batch_metadata` count shows how many incomplete steps lacked host-side shape information on at least one rank. The controller excludes fully idle steps from the coverage denominator and starts a new baseline after a recorder reset.

Compare `baseline_forward_p95_ms` and `trial_forward_p95_ms` in `last_trial` when the trial has enough matched samples. These percentiles pool sampled target forwards across matched batch shapes. The controller weights baseline samples to match the trial's batch-shape frequencies. Monitor request TTFT and TPOT separately.

The controller also compares sampled logical expert traffic by source rank and layer. `last_trial.routing_overlap` is the shared fraction of the two normalized route distributions during the baseline replay and the trial. A value of 1 means the same proportions. Below 0.75, or with no routed traffic to compare, the controller restores the previous interval. You can inspect `timing_outcome` when this routing check changes the decision. A rejected candidate can be tried again when comparable timings are available and either the batch-shape overlap or the routing overlap with the earlier workload drops below 0.75.

To pin an interval on a running recommend or auto worker, send an administrator command. A successful response acknowledges the request. Read back `effective_interval` and `applied_at_step` to verify application. Workers process commands at shared forward boundaries (at most 32 eligible steps apart), including when an interval is pinned. Repeating the active policy without an interval preserves any trial in progress. Switching policies during a trial without supplying a number restores the last confirmed interval. Supplying an explicit interval applies that value. Interrupted trials record their outcome in `last_trial`. A fixed pin overrides a trial and lasts until the next command or restart. To resume, send the same request with `{"eplb_interval":{"policy":"auto"}}`.

```bash
curl -fsS -X POST http://localhost:30000/set_internal_state \
  -H "Authorization: Bearer ${SGLANG_ADMIN_API_KEY}" \
  -H 'Content-Type: application/json' \
  -d '{"eplb_interval":{"policy":"fixed","interval":4000}}'
```

For more details, refer to the [EPLB Section in the Large-Scale EP Blog](https://lmsys.org/blog/2025-05-05-large-scale-ep/#expert-parallelism-load-balancer) and the [EPLB Repository](https://github.com/deepseek-ai/eplb).


## Ascend NPU Guidance
### Guidance on SGLang configuration in Ascend NPU
- `--moe-a2a-backend` only supports `deepep` and `ascend_fuseep` backends,

    - `deepep`: The mechanism is consistent with the above description.

    - `ascend_fuseep`: Offer a large fused operator which integrates all operations between dispatch and combine to boost MoE computation. Only used for decode stage in PD Disaggregation Mode.

- `--moe-runner-backend` parameter does not need to be configured.

- `--deepep-mode`:

    - In PD mixed mode, please set `--deepep-mode auto`.

    - In PD Disaggregation Mode, prefill instance sets `--deepep-mode normal`, and decode instance sets `--deepep-mode low_latency`.

### DeepEP Ascend Introduction
DeepEP Ascend is the adapted version of the DeepEP communication library for Huawei Ascend NPUs, specifically designed for Mixture-of-Experts (MoE) model Expert Parallelism (EP).
It supports the Ant-moving Function (Split the sequence length into rounds for streaming batch transmission) to optimize the buffer size occupied during collective communication in prefill stage, especially for long sequences.

Ant-moving Function can be enabled for both the dispatch and combine phases via the following environment variables:

- `DEEPEP_NORMAL_LONG_SEQ_PER_ROUND_TOKENS`: Enable ant-moving function in dispatch stage. Indicates the number of tokens transmitted per round on each rank, default 8192.

- `DEEPEP_NORMAL_LONG_SEQ_ROUND`: Enable ant-moving function in dispatch stage. Indicates the number of rounds transmitted on each rank, default 1.

- `DEEPEP_NORMAL_COMBINE_ENABLE_LONG_SEQ`: Enable ant-moving function in combine stage, default 0 (means disabled).

`DEEPEP_NORMAL_LONG_SEQ_PER_ROUND_TOKENS * DEEPEP_NORMAL_LONG_SEQ_ROUND` means input sequence length. When the input sequence length exceeds 8192, it is recommended to enable the ant-moving function in both dispatch and combine phase.

The environment variable `HCCL_BUFFSIZE` is used to configure the buffer size (MB) actually allocated. Its calculation formula is as follows:
```text Output
# Enable Ant-moving Function
HCCL_BUFFSIZE >= 2 * (102MB + 4MB + DEEPEP_NORMAL_LONG_SEQ_PER_ROUND_TOKENS * (hidden_size + hidden_size + hidden_size) * topk) + PADDING_BUFFSIZE

# Disable Ant-moving Function
HCCL_BUFFSIZE >= 2 * (102MB + 4MB + TOTAL_SEQ_LEN * (hidden_size + hidden_size) * topk) + PADDING_BUFFSIZE
```
Wherein the parameters are described as follows:

- `hidden_size`: hidden size in model config.

- `topk`: The number of selected routing experts.

- `TOTAL_SEQ_LEN`: input sequence length.

- `PADDING_BUFFSIZE`: A value of 20 or greater is recommended.
