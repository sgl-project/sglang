## Pageable host memory in Confidential Computing deployments

On CUDA Confidential Computing (CC) hosts that cannot register host memory,
set `SGLANG_HICACHE_PAGEABLE=1` and use the direct I/O backend:

```bash
SGLANG_HICACHE_PAGEABLE=1 python -m sglang.launch_server \
  --model-path /models/Qwen3.8-Flash-Next-FP8 \
  --tp-size 2 --ep-size 2 --no-ple-offload-embedding \
  --enable-hierarchical-cache \
  --hicache-io-backend direct \
  --hicache-mem-layout page_first_direct
```

This mode allocates ordinary CPU memory for attention KV, recurrent state,
and QSA indexer host pools. It does not call `cudaHostRegister` or unregister
those allocations during cleanup. Copies use the CUDA runtime rather than
kernels that access host pointers. MLA and DSA pools use device staging for
backup and CPU gathering followed by device scatter for load-back.
DSV4 pools stage whole-page transfers on the device. Partial-token transfers support the C4 V4 layout
(64 slots per 37,440-byte row). They copy values and scales separately,
preserving neighboring slots and page padding. These copies use bounded chunks and synchronize the submitting
thread before CPU memory is read or written.

Pageable mode supports the L2 host tier. Kernel I/O, unified memory, L3 storage,
external cache linkers, and HiSparse are rejected.
The L3 restriction also applies to runtime storage attachment. The host pool uses the
existing HiCache sizing and eviction policies. Staging allocations are separate
from the host pool; their size depends on the page geometry. Pageable copies
can synchronize the submitting thread, so timing results from pinned-memory
HiCache do not describe this mode.
