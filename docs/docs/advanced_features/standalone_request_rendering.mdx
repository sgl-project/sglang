---
title: "Standalone request rendering"
description: "Convert OpenAI chat and completion requests into SGLang token-in generate requests without starting an inference engine."
---

The standalone renderer reuses the Rust frontend's chat formatting, sampling
conversion, tokenizer, and context-length checks. It does not load model
weights or start a scheduler.

## Architecture

Both `sglang serve` and `sglang render` instantiate the same in-process
`RendererService`. The service owns rendering configuration and the chat
formatter. Its prepare-only methods also access the bounded CPU preprocessing
pool. It does not own scheduler, GPU worker, PD or DP transport, detokenizer, or
response-stream state.

The full inference server calls the service's lowering methods, then submits the
un-tokenized request through its shared frontend handle and existing request
FSM. The FSM remains the owner of sampling normalization, tokenization,
multimodal routing, and scheduler handoff. The standalone server calls the
service's prepare-only methods and serializes the result as a public `/generate`
body. Neither path calls the other through HTTP, and the standalone path does
not construct a placeholder engine client.

## Start the renderer

Use a Hugging Face model identifier or local model directory as `MODEL_PATH`.
The model must include a supported tokenizer configuration.

```bash
sglang render MODEL_PATH --host 0.0.0.0 --port 30000
```

The renderer serves these endpoints:

- `POST /v1/chat/completions/render`
- `POST /v1/completions/render`
- `GET /health`

## Render a request

Send the same body you would send to the corresponding OpenAI generation
endpoint.

```bash
curl http://localhost:30000/v1/chat/completions/render \
  -H "Content-Type: application/json" \
  -d '{
    "model": "MODEL_PATH",
    "messages": [{"role": "user", "content": "Explain radix caching."}],
    "max_completion_tokens": 128
  }'
```

The response is an SGLang-native request containing `rid`, `input_ids`,
`sampling_params`, `stream`, and the current logprob and hidden-state request
metadata. You can send this JSON directly to `/generate` on a compatible
SGLang inference server. Completion rendering returns an ordered array because
a completion request can contain multiple prompts or `n` choices. Chat
rendering currently requires `n=1` and returns one object.

## Output ownership

Rendering ends at the token-in request. Sending the result to `/generate`
returns SGLang-native generation output; the renderer does not turn that output
into an OpenAI Chat Completions or Completions response.

The normal OpenAI endpoints retain response-side reasoning splitting, tool-call
parsing, streaming shaping, and usage aggregation. A disaggregated token-in and
token-out frontend must retain the corresponding response context and perform
those steps after generation. That response-side contract is not part of the
initial standalone renderer.

## Transport and internal types

HTTP is the implemented wire format. Its response is a dedicated,
JSON-serializable `PreparedGenerateRequest` matching the current text fields
accepted by the public `/generate` endpoint. It is a prototype transport DTO,
separate from the mutable in-process `RendererRequest`, the server's internal
`GenerateRequest`, and the scheduler-facing MessagePack
`TokenizedGenerateReqInput`. Scheduler types are not a public renderer wire
contract.

A future render-only gRPC adapter should call `RendererService` directly and
preserve the same boundary. A minimal adapter can expose
`RenderChat(OpenAIJsonRequest)` and
`RenderCompletions(OpenAIJsonRequest)`, retaining the evolving OpenAI request as
JSON bytes rather than duplicating that schema in protobuf. The response uses a
dedicated protobuf message matching `PreparedGenerateRequest`, with one response
for chat and an ordered repeated response for completions. The
scheduler MessagePack shape must not be promoted to that public contract.
The prototype defines and round-trip tests this protobuf but does not register a
running service. It is distinct from a future native inference Tonic adapter,
which should call the same frontend handle as Axum rather than use the legacy
Python-bridge gRPC server. Adding either gRPC surface should add an adapter, not
a second rendering implementation.

## Current scope

The standalone renderer is text-only. Multimodal features and identities,
cache salt and extra keys, priority metadata, Responses API, and Anthropic
Messages API are not part of the initial contract. API-key authentication and
TLS termination are also not implemented on this standalone surface.
