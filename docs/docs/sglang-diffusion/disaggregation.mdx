A pipeline defines computation; a deployment assigns that computation to workers.
A **stage** is an operation in the pipeline. A **role** groups stages that run
together in one worker. A role can have multiple replicas, and multiple roles can
share a machine or GPU when their combined memory requirements fit.

You can use the existing encoder/denoiser/decoder presets, or an experimental
stage deployment for pipelines with declared stage contracts. Disaggregation
allows independent placement and scaling; it does not inherently reduce
single-request latency.

## Declarative stage deployment

This path currently targets Linux with NVIDIA GPUs and Mooncake. Support is
opt-in per pipeline: stage contracts, factories, and component loaders must all
support the chosen boundaries. A working monolithic pipeline alone is not
sufficient, and a placement file does not automatically make it splittable.

The following placement illustrates two independent encoding branches and two
downstream roles. Replace the stage IDs with those registered by your pipeline
before saving it as `deployment.json`; these names are schematic, not built-in
aliases:

```json
{
  "roles": {
    "prompt": {
      "stages": ["prompt_encode"],
      "endpoints": ["tcp://127.0.0.1:19000"],
      "node": "node1",
      "server_args": {"num_gpus": 1, "base_gpu_id": 0}
    },
    "reference": {
      "stages": ["image_encode"],
      "endpoints": ["tcp://127.0.0.1:19010"],
      "node": "node1",
      "server_args": {"num_gpus": 1, "base_gpu_id": 0}
    },
    "generate": {
      "stages": ["denoise"],
      "endpoints": ["tcp://127.0.0.1:19020"],
      "node": "node1",
      "server_args": {"num_gpus": 1, "base_gpu_id": 1}
    },
    "output": {
      "stages": ["decode", "postprocess"],
      "endpoints": ["tcp://127.0.0.1:19030"],
      "node": "node1",
      "server_args": {"num_gpus": 1, "base_gpu_id": 0}
    }
  }
}
```

Use the same model package, variant, numerical settings, and deployment file
on every host. Authenticate for gated models before starting. The example shares
GPU 0 between three worker processes; each loads its own required components and
transfer pool. This is process colocation, not shared weight storage.

Set `MODEL_PATH` to a compatible model package, then start this node's workers:

```bash
MODEL_PATH=/path/to/model-package
sglang serve --model-path "$MODEL_PATH" \
  --stage-deployment deployment.json --stage-node node1
```

Start the coordinator and the existing generation API in another terminal:

```bash
MODEL_PATH=/path/to/model-package
sglang serve --model-path "$MODEL_PATH" \
  --stage-deployment deployment.json \
  --host 127.0.0.1 --port 30000 --scheduler-port 18000
```

For an individually managed worker, replace `--stage-node` with:

```bash
sglang serve --model-path "$MODEL_PATH" \
  --stage-deployment deployment.json --stage-role generate \
  --stage-endpoint tcp://127.0.0.1:19020 \
  --num-gpus 1 --base-gpu-id 1 --scheduler-port 19120 --master-port 19220
```

The per-role `server_args` apply when using `--stage-node`; an individually
launched worker uses its own CLI arguments. Worker scheduler, master, and stage
ports must be distinct. For multiple machines, use routable private addresses,
assign roles to the appropriate `node`, and set `--disagg-p2p-hostname` on each
node. Node launch starts local processes; it does not provision machines or SSH
into other hosts.

Contracts define the dependencies: independent encoding branches can run in
parallel, and a downstream stage waits for its inputs. Role names do not imply
ordering. Within one role, stages keep their pipeline order and communicate
through the local request context, without a network hop. Sequential deployments
can transfer the request context automatically; explicit-field graphs transfer
only the declared fields their consumers need. Independent requests can use
different replicas of a role.

Stage workers skip standalone warmup because their inputs come from upstream
stages. Send representative requests through the coordinator before measuring
steady-state performance; warm up each input mode and worker replica you use.

### Declaring stage boundaries

Native pipelines can expose `stage_specs` using `StageSpec`, or deployments can
provide the same contracts in their top-level `stages` array:

For a sequential deployment, declare stage names and component requirements
without enumerating request fields:

```python
from sglang.multimodal_gen.runtime.disaggregation.deployment.plan import StageSpec

StageSpec("encode", components=("text_encoder", "tokenizer"))
StageSpec("denoise", components=("transformer", "scheduler"))
StageSpec("decode", components=("vae",))
```

When no stage declares `inputs` or `outputs`, the framework transfers the full
request context at role boundaries automatically, including nested model-specific
fields, sampling-parameter changes, and generator state. Tensors, including
tensors nested inside scheduler state, use the tensor transport rather than
Python object serialization. Process-local tracing, metrics, and model modules
are not migrated. Unsupported runtime objects fail explicitly.

This mode preserves sequential pipeline order, requires every stage to be
placed, and requires each role to contain consecutive stages. Group input
validation and encoding into the encoder, latent/timestep initialization and
denoising into the denoiser, and decoding/postprocessing into the decoder.
No per-model list of embeddings, masks, or metadata fields is needed.
The default terminal output is `result.output`; `outputs` can select other
terminal request fields. Full-context transfer favors correctness over minimum
communication volume and does not yet infer parallel encoder branches.

For explicitly optimized fan-out/join graphs, field contracts remain available:

```python
from sglang.multimodal_gen.runtime.disaggregation.deployment.plan import StageSpec

StageSpec(
    "vae_encode",
    inputs=("image_path",),
    outputs=("extra.image_latents",),
    components=("vae",),
    after=(),
)
```

Stage IDs must be nonempty, unique within the pipeline, and match the names
passed to `add_stage` or `add_stage_factory` exactly, including case. Without
an explicit name, `add_stage` uses the Python class name. Prefer stable semantic
IDs for new contracts; neither a model prefix nor `snake_case` is enforced.
Role names are independent deployment labels. Grouping stages does not reorder
them: the contract list must already be in topological order.

In each role's `stages`, you can also use zero-based integer indices, such as
`[0, 1, "denoise"]`. An index selects from the full contract list (the deployment's
top-level `stages`, if provided, otherwise the pipeline's `stage_specs`), before
role filtering. Names and indices may be mixed, but each stage can only be
assigned once. Negative indices, booleans, and out-of-range indices are rejected;
`"0"` is a name, not an index. Prefer names for configurations that must survive
pipeline updates, because inserting or reordering contracts changes indices.

`inputs` and `outputs` name request fields, `extra.<key>` fields, or
`result.<field>` outputs. The planner binds reads to their latest preceding
writer. By default a stage also depends on its predecessor; `after=()` removes
that control dependency, while data dependencies still apply. Use
`colocate_with` for stages sharing non-transferable runtime state. In this
explicit-field mode, keep generator, scheduler, module, and CUDA-event objects
local; declared tensors and JSON-safe metadata cross deployment boundaries.
Required fields that cannot be serialized fail explicitly rather than being
silently omitted.

A stage returning `OutputBatch` also exposes its output through the request
context for subsequent stages. Declare `output` as written when replacing it,
in addition to the terminal `result.output` field.

Use stage factories so unselected stages are not constructed. Component loaders
must honor the selected role's component set. The shared loader does this for
componentized pipelines; custom loaders need equivalent filtering.
Do not assume that old role-based module-name heuristics describe a custom stage.

Model transforms belong in postprocessing stages. Media saving and HTTP response
formatting remain at the output boundary. The standard decoding helper exposes
postprocessing separately; a specialized decoder that performs
additional work internally needs its own accurate contract before that boundary
can be split. Kernel implementations remain in stages/models, independent of
placement. The existing transfer-engine factory is the integration point for
custom communication implementations; both endpoints must obey the same buffer
registration and completion contract.

### Operational limits

- Use trusted private networking. Internal worker/coordinator RPC uses Python
  serialization and must not be exposed to untrusted clients.
- Size `--disagg-transfer-pool-size` for simultaneous receives and sends. Result
  leases and coordinator admission are bounded by
  `--disagg-max-slots-per-instance`; receive pools are separate from model memory.
  Cached stage tensors own their storage so reused model buffers cannot overwrite
  earlier results. Budget for retained outputs as well as weights and transfer pools.
  The head reports the maximum per-worker peak reserved memory, not the sum of
  memory used by processes sharing a GPU.
  Pending work is also bounded; overload returns an explicit error rather than
  accumulating an unbounded queue of raw media in host memory.
- A result is retained through fan-out until consumers finish or its lease
  expires. Unacknowledged transfers quarantine receive slots instead of reusing
  addresses that a remote sender might still write. Restart an exhausted worker
  after resolving the transport failure.
- TP/SP settings apply within each worker group. Transfers currently carry
  complete declared tensors; arbitrary sharded tensor layouts across groups
  need an explicit gather/reshard stage or colocation.
- For numerical comparisons, match the parallelism of every stage, including
  the VAE decode group, rather than only the denoiser's TP/SP settings.
- Placement must produce an acyclic role graph. Stateful loops and
  encode-while-decode streaming must stay within a compatible role; splitting a
  loop into independently retried operations is not supported.
- This is not a durable job queue and does not automatically replay failed
  inference or perform cross-node resource scheduling.
- Each worker executes one request at a time; use role replicas for concurrency.
  Per-worker dynamic batching is not enabled on this path. Client cancellation
  stops pending graph work and discards late results, but does not preempt an
  already-running GPU kernel or denoising loop.

### Single-Machine Example (Verified)

The following commands have been tested end-to-end on an 8×H200 machine with
`Wan-AI/Wan2.1-T2V-1.3B-Diffusers`. Each role runs on a separate GPU via
`--base-gpu-id`; the `server` head node requires no GPU.

```bash
# Terminal 1: Encoder (GPU 0)
sglang serve --model-path Wan-AI/Wan2.1-T2V-1.3B-Diffusers \
    --disagg-role encoder \
    --disagg-server-addr tcp://127.0.0.1:19655 \
    --scheduler-port 19000 \
    --num-gpus 1 --base-gpu-id 0

# Terminal 2: Denoiser (GPU 1)
sglang serve --model-path Wan-AI/Wan2.1-T2V-1.3B-Diffusers \
    --disagg-role denoiser \
    --disagg-server-addr tcp://127.0.0.1:19655 \
    --scheduler-port 19001 \
    --num-gpus 1 --base-gpu-id 1

# Terminal 3: Decoder (GPU 2)
sglang serve --model-path Wan-AI/Wan2.1-T2V-1.3B-Diffusers \
    --disagg-role decoder \
    --disagg-server-addr tcp://127.0.0.1:19655 \
    --scheduler-port 19002 \
    --num-gpus 1 --base-gpu-id 2

# Terminal 4: DiffusionServer head (no GPU, receives HTTP requests)
sglang serve --model-path Wan-AI/Wan2.1-T2V-1.3B-Diffusers \
    --disagg-role server \
    --encoder-urls  "tcp://127.0.0.1:19000" \
    --denoiser-urls "tcp://127.0.0.1:19001" \
    --decoder-urls  "tcp://127.0.0.1:19002" \
    --host 0.0.0.0 --port 22000 \
    --scheduler-port 19655

# Send request (video generation)
curl http://127.0.0.1:22000/v1/videos \
    -H "Content-Type: application/json" \
    -d '{"model": "Wan-AI/Wan2.1-T2V-1.3B-Diffusers", "prompt": "A curious raccoon exploring a garden, cinematic", "size": "832x480"}'
```

> **Tested result (8×H200):**
> Encoder 2.3 s (TextEncoding) → Denoiser 312.8 s (50 steps, layerwise offload) → Decoder 7.1 s (VAE decode).
> Total ~322 s for 81-frame 1024×1024 video.

> **Tip:** `--base-gpu-id` controls which physical GPU the role uses.
> Encoder and Decoder can share a GPU (e.g. both `--base-gpu-id 0`) to save resources,
> but make sure the combined GPU memory is sufficient.

### Multi-Machine Example

The exact same CLI pattern — just replace `127.0.0.1` with actual IPs and add
RDMA flags for direct transfer:

```bash
# Machine A (10.0.0.1): Encoder
sglang serve --model-path Wan-AI/Wan2.1-T2V-14B-Diffusers \
    --disagg-role encoder \
    --disagg-server-addr tcp://10.0.0.4:19655 \
    --scheduler-port 19000 \
    --num-gpus 1 \
    --disagg-p2p-hostname 10.0.0.1 --disagg-ib-device mlx5_0

# Machine B (10.0.0.2): Denoiser (4 GPUs with SP)
sglang serve --model-path Wan-AI/Wan2.1-T2V-14B-Diffusers \
    --disagg-role denoiser \
    --disagg-server-addr tcp://10.0.0.4:19655 \
    --scheduler-port 19001 \
    --num-gpus 4 --denoiser-sp 4 --denoiser-ulysses 2 --denoiser-ring 2 \
    --disagg-p2p-hostname 10.0.0.2 --disagg-ib-device mlx5_0

# Machine C (10.0.0.3): Decoder
sglang serve --model-path Wan-AI/Wan2.1-T2V-14B-Diffusers \
    --disagg-role decoder \
    --disagg-server-addr tcp://10.0.0.4:19655 \
    --scheduler-port 19002 \
    --num-gpus 1 \
    --disagg-p2p-hostname 10.0.0.3 --disagg-ib-device mlx5_0

# Machine D (10.0.0.4): DiffusionServer head
sglang serve --model-path Wan-AI/Wan2.1-T2V-14B-Diffusers \
    --disagg-role server \
    --encoder-urls  "tcp://10.0.0.1:19000" \
    --denoiser-urls "tcp://10.0.0.2:19001" \
    --decoder-urls  "tcp://10.0.0.3:19002" \
    --host 0.0.0.0 --port 30000 \
    --scheduler-port 19655 \
    --disagg-dispatch-policy max_free_slots
```

> ZMQ handles startup order gracefully — instances and head can start in any order.

### GLM-Image distributed mode

GLM-Image can batch AR generation in the head and dispatch the resulting prior
tokens to distributed denoiser workers. Each worker runs prompt/glyph preparation,
DiT, and VAE decoding locally; no latent or embedding tensors are transferred.

The following 16-device deployment uses devices 0-1 for the external AR server
and devices 2-15 for 14 independent batch-1 Cache-DiT denoisers.

```bash
# Run 14 distributed denoisers
DISAGG_SERVER="tcp://127.0.0.1:19655"
MODEL_PATH="zai-org/GLM-Image"
BASE_MASTER_PORT=29005

export SGLANG_CACHE_DIT_FN=2
export SGLANG_CACHE_DIT_BN=1
export SGLANG_CACHE_DIT_WARMUP=4
export SGLANG_CACHE_DIT_RDT=0.4
export SGLANG_CACHE_DIT_MC=4
export SGLANG_CACHE_DIT_TAYLORSEER=true
export SGLANG_CACHE_DIT_TS_ORDER=2
export SGLANG_CACHE_DIT_ENABLED=true

worker_pids=()

cleanup() {
    trap - EXIT
    if ((${#worker_pids[@]})); then
        kill "${worker_pids[@]}" 2>/dev/null || true
        wait "${worker_pids[@]}" 2>/dev/null || true
    fi
}

trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM

for i in $(seq 2 15); do
    scheduler_port=$((19001 + i))
    master_port=$((BASE_MASTER_PORT + i))

    sglang serve \
        --model-path "$MODEL_PATH" \
        --disagg-role denoiser \
        --disagg-server-addr "$DISAGG_SERVER" \
        --srt-encoder-url http://127.0.0.1:30020 \
        --scheduler-port "$scheduler_port" \
        --master-port "$master_port" \
        --num-gpus 1 \
        --base-gpu-id "$i" \
        --denoiser-sp 1 \
        --cfg-parallel-size 1 \
        --batching-max-size 1 \
        --dit-cpu-offload false \
        --attention-backend fa &
    worker_pids+=("$!")
done

# Stop all denoisers if any worker exits or fails during startup.
wait -n "${worker_pids[@]}"
```

```bash
sglang serve \
  --model-path ./zai-org/GLM-Image/vision_language_encoder/ \
  --tokenizer-path ./zai-org/GLM-Image/processor/ \

  --device npu \
  --attention-backend ascend \
  --disable-fast-image-processor \
  --tp-size 2 \
  --host 0.0.0.0 \
  --port 30020 \
  --mem-fraction-static 0.8

```

## Transfer Mechanism

Tensor data between adjacent roles is transferred via a P2P transfer engine. The DiffusionServer routes control messages and request metadata; tensors flow directly between workers. Uploaded reference files are forwarded inline as request metadata.

**mooncake-transfer-engine** is required for disaggregated diffusion. It provides RDMA for direct GPU-to-GPU data movement.

The GLM-Image distributed mode is an exception: it relays only prior token IDs
and request metadata over ZMQ and does not require Mooncake.

```bash
pip install mooncake-transfer-engine
```

### Transfer Flow

1. **Sender** stages output tensors in its transfer buffer, then notifies DiffusionServer.
2. **DiffusionServer** selects a downstream worker and reserves one of its preallocated receive slots. If none fits, it sends `transfer_alloc` and waits for `transfer_allocated`.
3. **DiffusionServer** sends `transfer_push` to the sender with the receiver's session and destination address.
4. **Sender** pushes the tensors through Mooncake and reports `transfer_pushed` after completion.
5. **DiffusionServer** sends `transfer_ready` to the receiver and releases the sender's scheduling slot.
6. **Receiver** loads the tensors on its transfer stream and executes its stages. Receive prefetch can overlap the previous request's compute.

Decoder results (final output) flow back through DiffusionServer as raw ZMQ frames to the HTTP client.

## Python API

For programmatic single-machine deployment, `launch_pool_disagg_server()` is available. It spawns its workers, and each child re-executes this script's module scope before initializing its platform, so keep the diffusion imports inside the guard:

```python
if __name__ == "__main__":
    from sglang.multimodal_gen.runtime.launch_server import launch_pool_disagg_server
    from sglang.multimodal_gen.runtime.server_args import ServerArgs

    server_args = ServerArgs.from_kwargs(
        model_path="Wan-AI/Wan2.1-T2V-14B-Diffusers",
        denoiser_sp=4, denoiser_ulysses=2, denoiser_ring=2,
        disagg_ib_device="mlx5_0",
    )

    launch_pool_disagg_server(
        server_args,
        encoder_gpus=[[0]],
        denoiser_gpus=[[1, 2, 3, 4], [5, 6, 7, 8]],
        decoder_gpus=[[0]],
    )
```

## Architecture

```
Client ─── HTTP (port 30000) ──► FastAPI Server
                                      │
                                      ▼
                              DiffusionServer (ROUTER, scheduler_port)
                              ┌───────┼───────┐
                   PUSH work  │       │       │  PUSH work
                              ▼       │       ▼
                    Encoder[0..N]     │    Decoder[0..K]
                              │       │       ▲
                   P2P tensor │       │       │ P2P tensor
                   transfer   ▼       │       │ transfer
                          Denoiser[0..M] ─────┘
                                      │
                    PULL results ◄────┘  (decoder → DS → client)
```

### Request State Machine

```
PENDING → ENCODER_WAITING → ENCODER_RUNNING → ENCODER_DONE
                                                    │
                        DENOISING_WAITING → DENOISING_RUNNING → DENOISING_DONE
                                                                       │
                                    DECODER_WAITING → DECODER_RUNNING → DONE
```

Any state can transition to `FAILED` or `TIMED_OUT`.
