### DeepSeek-V4.1 on Ascend910

On Ascend910 (`ascend910_93`, architecture `2201`), the low-ratio attention
backend needs five `sgl-kernel-npu` operators:
`sparse_flash_mla`, `sparse_flash_mla_metadata`, `lightning_indexer_v2` (including
candidate selection), `sparse_lightning_indexer`, and `compressor_v2`. A wheel
with only the Python wrappers is not sufficient. This requirement is specific
to DeepSeek-V4.1 on this target; it does not change the general installation matrix above.

To build the [CANN 9.2.0 operator bundle](https://github.com/sgl-project/sgl-kernel-npu/blob/9503fb118bf919bc35be1756b2f713587fc2f272/third_party/profiles/cann-9.2.0/ops_transformer.json),
start from a fresh checkout of that kernel revision on Ascend910 with CANN 9.2.0 and
its environment loaded. The [CompressorV2 component tests](https://github.com/sgl-project/sgl-kernel-npu/pull/958)
used Python 3.12.15 and torch/torch-npu 2.13.0. From the kernel repository root, run:

```bash
python3 setup.py --arch-version 2201 --ops all --artifact wheel --third-party ops_transformer -j8
python3 -m pip install --no-deps --force-reinstall output/sgl_kernel_npu-*.whl
```

If imports succeed but a native operator is missing or has the wrong signature,
test the installed wheel on the target device before starting the server:

```bash
python3 -m pytest -rs --enable-perf=false tests/python/operators/attention/test_sparse_flash_mla.py \
  tests/python/operators/indexer/test_lightning_indexer_v2.py \
  tests/python/operators/attention/test_compressor_v2.py
```

**For most users, the Docker image is the recommended path.** It is the most convenient option: the matched component
set from the [version mapping table](#component-version-mapping-for-sglang) comes pre-installed, and validated image
builds are tested as a whole. Installing from source is the more flexible option: you choose every component version
and control the build yourself, with no prebuilt binaries you cannot inspect. Whichever path you take, strictly follow
the version mapping table and do not mix versions across CANN sets.

### Method 1: Installing from source with prerequisites

The steps in this method install the component set from the [version mapping table](#component-version-mapping-for-sglang).

#### Python Version

**The CANN 9.2.0 set requires `python==3.12`.** If you don't want to break
system pre-installed python, try installing with [conda](https://github.com/conda/conda).

```bash Command
conda create --name sglang_npu python=3.12
conda activate sglang_npu
```

**Note on Anaconda repository restrictions**

If you encounter an error like “Terms of Service have not been accepted” during the conda create step, the default Anaconda repository is blocking package downloads. To resolve this, configure a mirror (e.g., Tsinghua Open Source Mirror):

```bash Command
# Add Tsinghua mirrors
conda config --add channels https://mirrors.tuna.tsinghua.edu.cn/anaconda/pkgs/main/
conda config --add channels https://mirrors.tuna.tsinghua.edu.cn/anaconda/cloud/conda-forge/
conda config --set show_channel_urls yes
conda config --remove channels defaults
```

Edit the system-level conda config to remove any hardcoded defaults, e.g., `vi ~/miniconda3/.condarc`.
Then remove the failed environment and recreate it:

```bash Command
conda clean -i
conda env remove -n sglang_npu
conda create --name sglang_npu python=3.12
conda activate sglang_npu
```

#### CANN

Prior to starting work with SGLang on Ascend, you need to install CANN Toolkit, Kernels operator package and NNAL version 9.2.0, check the [installation guide](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/920/softwareinst/instg/instg_0008.html?OS=openEuler&InstallType=local)

#### MemFabric-Hybrid

If you want to use PD disaggregation mode, you need to install MemFabric-Hybrid. MemFabric-Hybrid is a drop-in replacement of Mooncake Transfer Engine that enables KV cache transfer on Ascend NPU clusters.

```bash Command
# The index serves both aarch64 and x86_64 wheels
pip install memfabric-hybrid==1.5.0.dev20261119 --extra-index-url https://ascend.devcloud.huaweicloud.com/pypi/simple/

# Install the device-specific MemFabric kernels.
# --soc-version is A5 on the 950PR/DT Series, A3 on the A3 Series.
mfcli kernel install --soc-version <A5|A3>
```

#### PyTorch and PyTorch Framework Adapter on Ascend

```bash Command
PYTORCH_VERSION=2.13.0
TORCHVISION_VERSION=0.28.0
TORCH_NPU_VERSION=2.13.0
pip install torch==$PYTORCH_VERSION torchvision==$TORCHVISION_VERSION --index-url https://download.pytorch.org/whl/cpu
pip install torch_npu==$TORCH_NPU_VERSION --extra-index-url https://ascend.devcloud.huaweicloud.com/pypi/simple/
```

If you are using other versions of `torch` and install `torch_npu`, check [installation guide](https://github.com/Ascend/pytorch/blob/master/README.md)

After the installation, verify that PyTorch can compute on the NPUs — it should print `True`, then a small tensor
computed on the device:

```bash Command
python3 -c "import torch; print(torch.npu.is_available()); x = torch.arange(1, 5, dtype=torch.float32).npu(); print(x * x)"
```

The expected second line is `tensor([1., 4., 9., 16.], device='npu:0')` — the squares of `1, 2, 3, 4`, computed on the
device. You may also see some compatibility warnings caused by device differences; they are safe to ignore.

#### Triton on Ascend

We provide our own implementation of Triton for Ascend.

```bash Command
# On an x86_64 host, replace aarch64 with x86_64 in the wheel URL
pip install https://ascend-triton-open.obs.cn-north-4.myhuaweicloud.com/triton-ascend/20261105160244/triton_ascend-3.6.0%2Bdev20261105160244-cp312-cp312-manylinux_2_27_aarch64.manylinux_2_34_aarch64.whl
```

For installation of Triton on Ascend nightly builds or from sources, follow [installation guide](https://github.com/triton-lang/triton-ascend/blob/main/docs/en/installation_guide.md)

#### SGLang Kernels NPU

We provide SGL kernels for Ascend NPU, check [installation guide](https://github.com/sgl-project/sgl-kernel-npu/blob/main/python/sgl_kernel_npu/README.md).

<Note>
Gemma-family models (including Qwen3.5) call `sgl_kernel_npu.norm.gemma_rmsnorm`,
whose implementation is chosen when the wheel is built: the native `torch_npu`
operator for A2/A3 Series, and ACLNN RMSNorm for 950PR/DT Series, which does not
register that operator. **950PR/DT Series must install the `950` release
package** (`950` appears in the asset name), or build from source with
`bash build.sh -a kernels Ascend950PR_9599`, the target that package is built
with. On 950PR/DT, an `a2` or `a3` package fails on the first Gemma forward,
and so does a package from a release that predates this module; check with
`python -c "import sgl_kernel_npu.norm.gemma_rmsnorm"`.
</Note>

#### DeepEP-compatible Library

We provide a DeepEP-compatible Library as a drop-in replacement of deepseek-ai's DeepEP library, check
the [installation guide](https://github.com/sgl-project/sgl-kernel-npu/blob/main/python/deep_ep/README.md).
It is optional and needed only when serving MoE models with expert parallelism through
`--moe-a2a-backend deepep`; plain TP deployments can skip it.

### Method 2: Using Docker Image

#### Install Ascend Docker Runtime

The container commands in this documentation rely on
[Ascend Docker Runtime](https://www.hiascend.com/document/detail/en/mindcluster/latest/clustersched/schedulingug/docs/en/scheduling/01_introduction/01_component_description.md#ascend-docker-runtime) on the host.
It is a container runtime plugin (an OCI prestart hook) that reads the `ASCEND_VISIBLE_DEVICES` environment variable
passed to `docker run`: it binds the selected NPU device nodes (including `/dev/davinci_manager` and `/dev/hisi_hdc`)
into the container and mounts the host driver dependencies the NPU stack needs. Without the runtime,
`ASCEND_VISIBLE_DEVICES` is ignored and none of this is mounted automatically.

Install it once per host as `root` (skip this step if the host already has it). Download the `.run` package
from the [MindCluster releases page](https://gitcode.com/Ascend/mind-cluster/releases), then:

```bash Command
# ============================================================
# Before running, replace the following placeholders:
#   <version>: Ascend Docker Runtime package version you downloaded
#   <arch>: host architecture, e.g. aarch64 or x86_64
# ============================================================

chmod u+x Ascend-docker-runtime_<version>_linux-<arch>.run
./Ascend-docker-runtime_<version>_linux-<arch>.run --install
systemctl daemon-reload && systemctl restart docker
```

Verify that the runtime is registered as Docker's default runtime:

```bash Command
docker info --format 'default={{.DefaultRuntime}}'
```

The output must be `default=ascend`. If it prints `default=runc`:

1. If the `Runtimes:` line of `docker info` lists `ascend`, either pass `--runtime ascend` to every `docker run`,
or set `"default-runtime": "ascend"` in `/etc/docker/daemon.json` and restart Docker.
2. If `ascend` is missing from `Runtimes:`, rerun the installation above and restart Docker.

**What the runtime handles and what stays in the command:**

| Handled automatically by the runtime | Still set by the `docker run` command |
|---|---|
| NPU device nodes (`/dev/davinci*`, `/dev/davinci_manager`, `/dev/hisi_hdc`) for the ids in `ASCEND_VISIBLE_DEVICES` | The image tag |
| Driver libraries (`/usr/local/Ascend/driver/lib64`, `/usr/local/Ascend/driver/include`) | The device ids in `ASCEND_VISIBLE_DEVICES`: `0-15` for a full A3 Series node (ids are DIE-level, see the [glossary](/docs/hardware-platforms/ascend-npus/reference/glossary#hardware)), `0-7` for a full 950PR/DT Series node |
| `/usr/local/dcmi`, `/usr/local/bin/npu-smi`, `/var/queue_schedule` | Extra mounts such as `/usr/local/Ascend/driver`, `/usr/local/Ascend/firmware`, `/etc/ascend_install.info`, `/usr/local/sbin`, model weights, and the HF cache |

`ASCEND_VISIBLE_DEVICES` accepts a single id (`0`), a comma-separated list (`0,1`), an inclusive range (`0-15`),
a mixed form (`0-3,7`), and `void` for a container without any NPU.

If the runtime cannot be installed on the host (for example, no `root` access), containers can still be started
with explicit `--device` and `--volume` flags — see
[Running containers without Ascend Docker Runtime](/docs/hardware-platforms/ascend-npus/faq#9-running-containers-without-ascend-docker-runtime) in the FAQ.

2. Build an image based on Dockerfile

The Dockerfile clones SGLang from GitHub during the build and does not use the local checkout, which only provides
`npu.Dockerfile`. Pass `SGLANG_TAG` to build a specific branch or tag.

```bash Command
# Clone the SGLang repository to obtain the Dockerfile
git clone https://github.com/sgl-project/sglang.git
cd sglang/docker

# Build the docker image
# Required arguments:
#   TARGETARCH: target architecture, e.g., amd64, arm64
#   DEVICE_TYPE: target hardware, a3 or 950. The Dockerfile defaults to 950, so A3 Series builds must set a3.
# Optional arguments:
#   SGLANG_TAG: SGLang branch or tag to clone, e.g., main (default)
#   CANN_VERSION: CANN version, e.g., 9.2.0 (default)
#   SGLANG_KERNEL_NPU_TAG: sgl-kernel-npu release tag (default 2026.11.0.post14)
# If there are network errors, please modify the Dockerfile to add ARG HTTP_PROXY/HTTPS_PROXY and set them as ENV.
docker build \
    --build-arg TARGETARCH=<arch_tag> \
    --build-arg DEVICE_TYPE=<a3|950> \
    --build-arg SGLANG_TAG=<branch_or_tag> \
    -t <image_name> -f npu.Dockerfile .
```

## System Settings

### CPU performance power scheme

The default power scheme on Ascend hardware is `ondemand` which could affect performance, changing it to `performance` is recommended.

```bash Command
echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor

# Make sure changes are applied successfully
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor # shows performance
```

### Disable NUMA balancing

The kernel's background NUMA page migration adds memory-bandwidth overhead and latency jitter to SGLang's large resident
working set (weights and KV cache); disabling it keeps serving latency stable.

```bash Command
sudo sysctl -w kernel.numa_balancing=0
# Check
cat /proc/sys/kernel/numa_balancing # shows 0
```

### Prevent swapping out system memory

```bash Command
sudo sysctl -w vm.swappiness=10

# Check
cat /proc/sys/vm/swappiness # shows 10
```

#### PD Disaggregation Scene

PD disaggregation requires the prefill server, the decode server, and the router to communicate with one another.
Make sure the hosts can reach one another over the network and that the `PREFILL_IP:FREE_PORT` store address is
accessible from every node. The example below runs all three on a single machine, each using its own port and NPU
(via `--base-gpu-id`); the same steps apply to a multi-node cluster, provided the hosts can reach one another.

1. Launch Prefill Server

Model weights: set `HF_TOKEN` to download automatically, or replace the model ID in `--model-path` with a local

```bash Command

# FREE_PORT: any available port
```

3. Launch Router

The router is the `sgl-router` binary. It is pre-installed in the Docker image at `/usr/local/bin/sgl-router`; otherwise
install it with `pip install sgl-router`, or see
[installing sgl-router](/docs/advanced_features/dp_dpa_router_guide#quick-start-for-sgl-router) for the container image
and building from source.

```bash Command
sgl-router \
    --model-id meta-llama/Llama-3.1-8B-Instruct \
    --no-tokenizer \
    --worker-urls http://127.0.0.1:30001 http://127.0.0.1:30002 \
    --host 127.0.0.1 \
    --port 30000
```

<Note>
`--worker-urls` lists the prefill and decode servers together: the router reads each server's role and the prefill
bootstrap port from the server itself. `--model-id` must match the servers' model name, which is their
`--served-model-name`, or their `--model-path` when that flag is not set. `--no-tokenizer` leaves tokenization to the
servers. Wait for `curl http://127.0.0.1:30000/readiness` to return HTTP 200, which means both servers are registered.
</Note>

## Testing the Service

Once the server prints `The server is fired up and ready to roll!` in the logs, it is ready to accept requests.

### Which port to send requests to

The port you use depends on your deployment mode:

| Scenario | Where to send requests |
|---|---|
| Non-PD (single server) | The server's `--port` (e.g., `30000` in the examples above) |
| Non-PD (multi-node) | The primary node's (`--node-rank 0`) `--port`; do **not** send requests to worker nodes |
| PD disaggregation | The router's `--port` (e.g., `30000` in the examples above); do **not** send requests directly to prefill or decode servers |

<Tip>
SGLang defaults to port `30000` when `--port` is not specified. The examples in this guide use explicit ports for clarity.
</Tip>

### Health Check

```bash Command
curl http://127.0.0.1:30000/health
```

A successful response returns HTTP 200 with an empty body. On the PD router, `/health` only shows that the router is
up; use `/readiness` to check that the prefill and decode servers are registered.

### Generate (Native Endpoint)

```bash Command
curl http://127.0.0.1:30000/generate \
  -H "Content-Type: application/json" \
  -d '{
    "text": "What is the capital of France?",
    "sampling_params": {"temperature": 0, "max_new_tokens": 128}
  }'
```

The expected output should contain "Paris".

### Chat Completions (OpenAI-Compatible)

```bash Command
curl http://127.0.0.1:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "meta-llama/Llama-3.1-8B-Instruct",
    "messages": [{"role": "user", "content": "What is the capital of France?"}]
  }'
```

Some models return responses accompanied by thinking process content. To disable this output, configure parameters as follows:

```bash Command
curl http://127.0.0.1:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Eco-Tech/Qwen3.5-27B-w8a8-mtp",
    "messages": [{"role": "user", "content": "What is the capital of France?"}],
    "chat_template_kwargs": {"enable_thinking": false}
  }'
```

The expected output should contain "Paris".

## FAQ

### How do I provide model weights?

The launch commands in this guide pass a Hugging Face model ID (e.g., `meta-llama/Llama-3.1-8B-Instruct`) to
`--model-path`. Pick one way to provide the weights:

- **Automatic download**: export `HF_TOKEN` (required for gated models such as Llama) and let SGLang download the
  weights from Hugging Face on first launch; they are cached under `~/.cache/huggingface` and reused afterwards.
- **Pre-downloaded weights**: download the weights to the machine yourself, then replace the model ID in the commands
  with the local weights path, e.g., `--model-path /path/to/Llama-3.1-8B-Instruct`.

When running in Docker, the `drun` alias mounts `~/.cache/` from the host, so weights already in the host's Hugging
Face cache are visible inside the container.
