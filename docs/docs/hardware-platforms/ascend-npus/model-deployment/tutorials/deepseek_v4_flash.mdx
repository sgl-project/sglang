## Introduction

DeepSeek-V4-Flash is a Mixture-of-Experts (MoE) large language model developed by DeepSeek. It combines hybrid sparse
attention (CSA + HCA) with the DeepSeekMoE architecture and supports a 1M-token context length. The 0731 checkpoint
used in this tutorial includes a DSpark draft head for speculative decoding.

This document demonstrates the deployment of DeepSeek-V4-Flash on Ascend NPUs using SGLang, covering both the A3
Series and the 950PR/DT Series (SoC name A5), including single-node PD mixed deployment, multi-node PD disaggregation
mode, DSpark speculative decoding with Static and optional Compact verification, HiCache L2/L3, feature configuration,
and performance optimization.

Compact combines confidence estimates with a profiled steps-per-second (SPS) cost table to select per-request
draft-prefix lengths and pack them for target verification, reducing logical verification work. HiCache extends
KV caching to host memory (L2) and optional storage backends (L3), enabling greater prefix reuse in long-context
and multi-turn workloads. The Compact workflow in this document is scoped to single-node PD mixed deployment.

This document is validated and written based on **SGLang v0.5.16**. The current model (DeepSeek-V4-Flash) is fully
supported in this version. To use the latest features (e.g., PD disaggregation, speculative decoding), it is
recommended to use v0.5.16 or a later version.

## Online service deployment

### Single-node PD mixed deployment

Single-node deployment completes both prefill and decode within the same node (PD mixed mode), suitable for scenarios
with limited hardware resources. Select the script for your platform and run it inside the container.

The DSpark examples below use one full 910(A3) node with 16 NPU dies (TP=16, DP Attention=16), or one full 950(A5)
node with eight NPU devices (TP=8, DP Attention=8). Save the matching script and set `MODEL_PATH` to the local weights.
SGLang uses Static verification by default. To enable Compact after profiling, set
`SGLANG_RAGGED_VERIFY_MODE=compact` and pass `--speculative-dspark-sps-table-path` when restarting the matching script.

Save as `launch_dspark_a3.sh`. This full-node DSpark example uses the W8A8 checkpoint and ModelSlim draft loading;

#### DSpark Compact (optional)

Static is the upstream default. For the profiler's default one-dimensional sweep, first run a Static server, then
generate an SPS table, stop the server, and restart in Compact mode with that table. The profiler connects to the
running server; it does not launch one. Profile a separate table for each hardware, checkpoint, quantization,
parallelism, draft width, and graph configuration that changes step cost.

Keep NPU graphs enabled, pipeline parallelism at one, and attention context parallelism at one for these examples.
With DP Attention, retain `--enable-dp-lm-head`. Compact needs trained confidence weights or the runtime's supported
online estimator; Static alone does not require a trained Confidence Head.

**1. Start the Static profiling server.** First start a Static DSpark service using the command for your hardware;
then generate the SPS table in the next step. The default diagonal profiler requires
`SGLANG_DSPARK_ENABLE_SPS_RECORD=1` and `SGLANG_SIMULATE_ACC_LEN=1.0`; these are profiling settings,
not accuracy-evaluation or production defaults.

**4. Verify serving and scheduling.** Check the startup log for
`DSpark ragged-verify scheduler enabled`, `mode=compact`, and the intended SPS-table path.
The runtime warns when the cost table is uninitialized and the budget degenerates to verify-all; selecting the mode
alone is not evidence of token-budget savings. Send requests with the same API examples used for Static, then compare
scheduled verification lengths, actual graph sizes, acceptance, TTFT, TPOT, throughput, and completed-request counts.

For a five-token draft block, each Static window contains six positions including the anchor. With three requests,
Compact lengths `[6, 4, 2]` contain 12 logical verification positions instead of 18. Graph padding and DP agreement
can still keep the executed graph size unchanged. Keep prompts, sampling, thinking settings, concurrency, output
limits, and warmup fixed between Static and Compact; leave simulated acceptance unset during these checks.

For the complete benchmark data and additional single-node configurations, see
[DeepSeek-V4-Flash Best Practice — PD Mixed On A3 Series](/docs/hardware-platforms/ascend-npus/model-deployment/best-practices/deepseek_v4_flash#single-node-pd-mixed).

### HiCache L2 and L3 (optional)

HiCache extends prefix KV caching from NPU memory (L1) to host memory (L2), with an optional storage backend (L3).
It benefits repeated prefixes in long-context and multi-turn workloads; Compact changes decode verification work.
Size host memory for the whole deployment, including every worker's cache pools.

For L2 on Ascend, append the following arguments to the 910(A3) launch script. Use the Ascend `kernel_ascend` I/O backend
and let the runtime select its compatible memory layout. For 950(A5), first remove `--disable-radix-cache` from its
launch script before enabling HiCache.

```bash Command
MODEL_PATH=/path/to/DeepSeek-V4-Flash-0731-w8a8 \
bash launch_dspark_a3.sh \
    --enable-hierarchical-cache \
    --hicache-ratio 2 \
    --hicache-io-backend kernel_ascend \
    --hicache-write-policy write_through
```

`--hicache-write-policy` controls when device KV cache is backed up to host memory. This example explicitly uses
the default `write_through` policy, which proactively backs up cached KV for later reuse.

L2 requires no storage-backend flag. For L3, configure the chosen backend and additionally pass
`--hicache-storage-backend file`, `mooncake`, or another backend supported by the installed runtime. The `file` backend
uses node-local storage by default; set `SGLANG_HICACHE_FILE_BACKEND_STORAGE_DIR` to a mounted directory with sufficient
capacity when using it in a container. A storage-backend flag alone does not configure a remote storage service.

For backend setup, write and prefetch policies, and cache-hit validation, see
[HiCache Best Practices](/docs/advanced_features/hicache_best_practices). Keep cache settings identical when comparing
Static and Compact. Validate their combined configuration on the selected hardware; 950(A5) Compact remains pending validation.

## Functional verification

After the service is started, you can invoke the model by sending a prompt. The launch scripts set the served model
name to `deepseek-v4-flash`. Set `HOST` and `PORT` for 910(A3) (`127.0.0.1:6688`) or 950(A5) (`127.0.0.1:8001`):

```shell
# ============================================================
# Before running, update the following variables:
#   HOST: the server host address (e.g., localhost)
#   PORT: the server port number (e.g., 6688)
# ============================================================

curl http://${HOST}:${PORT}/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{
        "model": "deepseek-v4-flash",
```
