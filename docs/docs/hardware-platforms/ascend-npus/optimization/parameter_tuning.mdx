This page is for a server that already runs. Start from a minimal working launch (see the
[Model Tutorials](/docs/hardware-platforms/ascend-npus/model-deployment/tutorials) index in the sidebar), and leave the
heavy lifting — full launch scripts, multi-node topology, and the settings a deployment shape
requires (the PD roles, the KV-transfer backend and rendezvous store, the network interfaces) — to the per-model
**Best Practices** pages, each of which names the image it was validated on.

The page centers on one table. [Parameter Reference](#parameter-reference) lists every tuning parameter on Ascend —
the switches you batch-enable and the knobs you size — one row per parameter, with what it does, the trade-offs across
its values, and a validated reference value. Most of these parameters influence each other directly or indirectly, so
per-goal sub-lists inevitably miss some of them; the table is the complete inventory, and the rest of the page
navigates it:

1. **[How to Tune](#how-to-tune)** — the workflow: measure a baseline, batch-enable every applicable switch, then tune
   the knobs top-down, one at a time.
2. **[Tuning by Goal](#tuning-by-goal)** — where to start for a goal (TPOT, throughput, TTFT, OOM, long contexts), and
   how a PD-disaggregated deployment splits the values per role.
3. **[Feature Compatibility](#feature-compatibility)** — check a combination before enabling several features together.

Flag names and values change across releases, and the docs may at times fall out of sync with the code: the
best-practice pages pin the scripts of the image they were validated on, while this page tracks current builds. If a
flag or value here is rejected or has no effect on your build, query the repository for how that name evolved — an AI
assistant pointed at the codebase is a fast way to trace renames and removals — and check
[Supported Features](/docs/hardware-platforms/ascend-npus/reference/support_features) for per-flag support status.

## How to Tune

1. **Define the goal and measure a baseline.** Choose the target metric (TTFT, TPOT, throughput, or memory headroom) and
   benchmark the current configuration before changing anything. [Performance Testing](/docs/hardware-platforms/ascend-npus/evaluation/performance_testing)
   shows the command and how to read Mean TTFT/Mean TPOT. Record the seed, input/output lengths, and concurrency with
   every run. For a kernel-level view, use [Profiling](/docs/hardware-platforms/ascend-npus/optimization/profiling).
2. **Batch-enable the add-on optimizations, then verify three things.** Add every switch from the checklist below whose
   applicability matches your model and role, in one batch. These switches pay off as soon as they apply: there is no
   value to size. The kernel-fusion and stream-overlap switches that match your model class are typically the largest
   wins; the allocator and host settings are smaller but apply to every deployment; speculative decoding can cut
   per-token latency the most but is acceptance-rate dependent and needs its accuracy check. Then confirm, in order,
   that the server starts, that the
   [accuracy evaluation](/docs/hardware-platforms/ascend-npus/evaluation/accuracy_evaluation) passes (mandatory after
   speculative decoding), and that the benchmark improves or holds. If a step fails, remove the added switches one at a
   time until the culprit is found; nearly all failures are precondition violations stated in the switch's table row.
3. **Tune the knobs top-down, one at a time.** Fix the topology first (parallelism, PD disaggregation), then the
   load-shape parameters that consume memory ([`--chunked-prefill-size`](#chunked-prefill-size),
   [`--cuda-graph-max-bs-decode`](#cuda-graph-max-bs-decode), speculative depth), and size
   [`--mem-fraction-static`](#mem-fraction-static) last: activation and graph buffers are inputs to the memory budget.
   Communication settings come after that. Choices at one level bound what the levels below can achieve, and
   graph-level tuning cannot compensate for a wrong TP/EP split. Re-measure after every change, keep the better
   configuration, and record every configuration you benchmark so the results stay comparable.
4. **Verify before keeping it.** After quantization or speculative decoding, run the
   [accuracy evaluation](/docs/hardware-platforms/ascend-npus/evaluation/accuracy_evaluation). After any change, re-run
   the same benchmark. Keep the previous configuration so you can roll back.

The batch checklist for step 2, each switch linking to its row in [Parameter Reference](#parameter-reference):

| Switch | Applies when |
| --- | --- |
| [`SGLANG_NPU_USE_MLAPO=1`](#npu-use-mlapo) | DeepSeek-style MLA |
| [`SGLANG_USE_FIA_NZ=1`](#use-fia-nz) | DeepSeek-style MLA |
| [`SGLANG_NPU_USE_MULTI_STREAM=1`](#npu-use-multi-stream) | MoE models with shared experts — the DeepSeek, GLM, Qwen-MoE, and LongCat code paths all read it (set by the DeepSeek R1, DeepSeek V4-Flash, GLM-5.1/5.2, and Kimi K2.6 best practices; the Qwen3-Next best practice pins it to `0`) |
| [`SGLANG_USE_AG_AFTER_QLORA=1`](#ag-after-qlora) + `--enable-attn-tp-input-scattered` | Model with `q_lora_rank`; practically prefill-only |
| [`SGLANG_ENABLE_OVERLAP_PLAN_STREAM=1`](#overlap-plan-stream) | Speculative decoding on, no LoRA |
| [`--enable-dp-lm-head`](#enable-dp-lm-head) | Attention DP on |
| [`PYTORCH_NPU_ALLOC_CONF=expandable_segments:True`](#pytorch-npu-alloc-conf) | Always |
| [Host settings](#host-os-settings): CPU governor `performance`, `vm.swappiness=0`, `kernel.numa_balancing=0`, `kernel.sched_migration_cost_ns=50000`, [`SGLANG_SET_CPU_AFFINITY=1`](#set-cpu-affinity) | Always (commands run as root) |
| [Speculative decoding](#speculative-algorithm) | Model ships an MTP head (`NEXTN`), or you supply an external draft model (`EAGLE3`); verify accuracy after enabling |

To match the *Applies when* column against your model, read its `config.json`: MLA models carry `kv_lora_rank` (with
`q_lora_rank` additionally gating the gather-after-Q switch), MoE models with shared experts carry `n_shared_experts`,
and a NextN/MTP head appears as `num_nextn_predict_layers`.
[Supported Models](/docs/hardware-platforms/ascend-npus/reference/support_models) lists the validated model families,
and each model's best-practice page shows which of these switches its script sets — if you launched from one, most are
already set, and the checklist then tells you what the script set and why.

The remaining switches are conditional: they are also on/off, but the payoff depends on the workload, so they are not
part of the batch. Enable one only when evidence from benchmarks, metrics, or the traffic shape says its condition
holds — the condition, and what happens when it is not met, are stated in the row's trade-offs:
[`SGLANG_SCHEDULER_SKIP_ALL_GATHER=1`](#scheduler-skip-all-gather) (balanced DP load),
[`--enable-eplb`](#enable-eplb) (measured expert imbalance), prefix caching
([`--disable-radix-cache`](#disable-radix-cache), shared prefixes),
[`--deepep-dispatcher-output-dtype int8`](#deepep-dispatcher-output-dtype) (accuracy budget),
[`TASK_QUEUE_ENABLE=2`](#task-queue-enable) (the role captures no graphs), and
[`HCCL_OP_EXPANSION_MODE=AIV`](#hccl-op-expansion-mode) (never on Atlas A2 systems with DeepEP).

Knob values come in two shapes, and they are swept differently. **Discrete** knobs have a small valid set — there is
nothing between two adjacent values — so benchmark each candidate. **Range** knobs have a useful interval bounded by a
different failure mode at each end, so sweep in coarse steps (×2 for token counts, small increments for the memory
fraction). Every row in [Parameter Reference](#parameter-reference) leads its trade-offs with its shape —
**Discrete**, **Range**, or **Switch** — followed by what each discrete value buys, or what raising and lowering a
range knob buys and costs. Raising such a knob buys capacity or coverage and spends latency or memory; lowering it
reverses the trade.

## Parameter Reference

Every tuning parameter on Ascend, in one table. The **Feature** column groups the rows by subsystem; the **Purpose**
column says what the parameter does and when it applies; the **Trade-offs** column carries the shape —
**Discrete** rows give the constraint and what larger or smaller choices buy, **Range** rows state what raising and
what lowering buys and costs with the failure mode at each end, and **Switch** rows state the enable condition and
the risk of enabling the switch when that condition is not met.

Unless a row says otherwise, the **Reference Value** comes from the published DeepSeek V3.2 PD configuration on 32
NPUs and is a starting point from that validated deployment, not a flag default. On a single mixed node there are no
roles to split: start from the raw defaults and let [Tuning by Goal](#tuning-by-goal) drive your changes — the
per-role values show where a large two-role deployment converged. Raw defaults for most flags are in
[Supported Features](/docs/hardware-platforms/ascend-npus/reference/support_features), and the NPU environment
variables are listed in [Ascend NPU Environment Variables](/docs/hardware-platforms/ascend-npus/reference/environment_variables).
`—` means do not set the flag, and the trade-offs explain when that changes. A trailing condition narrows when a value
applies, as in `on (DeepSeek R1)`. Setup-only settings that have no value to tune — the network-interface variables
(`HCCL_SOCKET_IFNAME` / `GLOO_SOCKET_IFNAME`) and the multi-node topology flags (`--nnodes`, `--node-rank`,
`--dist-init-addr`) — are omitted: copy them from your model's best-practice script, because a wrong rank or an
unreachable interface hangs startup.

### Graph batch-size alignment

Decode buckets are filtered against a batch-size alignment. The alignment is `attn_tp_size` whenever a gathered buffer is
in use: attention DP, any MoE all-to-all backend, or an explicit `--moe-dense-tp-size`; otherwise it is `1`. Two-batch
overlap (two micro-batches per step) doubles the alignment, and context parallelism can raise it further. A bucket
survives when batch size × per-request decode tokens is a multiple of the alignment; with speculative decoding the draft
tokens already supply part of that multiple, so buckets below the alignment can survive. Buckets that miss
the alignment are dropped, and startup aborts if none survive.

In practice, set `--cuda-graph-max-bs-decode` to at least the alignment and to a multiple of it whenever attention DP, an
all-to-all backend, or `--moe-dense-tp-size` is in play. A dense model with plain TP has no such constraint.

Two defaults follow from this area. NPU prefill graphs are off by default, so no prefill graph flag is needed. And do
not use the deprecated `--disable-cuda-graph` on a mixed node: it also disables decode graphs there — use
`--cuda-graph-backend-decode=disabled` to disable only decode graphs. A dedicated prefill role that captures no graphs
may still carry it, as the published prefill scripts do; there it is redundant and harmless.

### Sizing the DeepEP dispatch buffer

Size `SGLANG_DEEPEP_NUM_MAX_DISPATCH_TOKENS_PER_RANK` to the maximum number of tokens one rank dispatches per decode
iteration: running requests per rank × `--speculative-num-draft-tokens` with speculative decoding, or just the running
requests per rank without it.

The published value `8` leaves headroom over its benchmark load: 8 concurrent requests over DP 8 is one request per
rank, which is `1 × 4 = 4` dispatched tokens per iteration, half the buffer. Serving the full `--max-running-requests 32`
cap would need `(32 / 8) × 4 = 16`, so raise the value when you serve more concurrency than the benchmark did.

One consequence follows from how the value is used: low-latency dispatch pads to the configured value every iteration,
so an oversized buffer avoids the runtime failure but adds padding cost on every step. And `ascend_fuseep` gives the
variable different semantics (its default `--fuseep-mode 2` treats it as received-token capacity), so the DeepEP
formula does not carry over.

## Tuning by Goal

Where to start for common goals, ordered by expected impact. Each goal is a thin index into
[Parameter Reference](#parameter-reference): the entries below name the parameters with the largest expected effect,
and the full cost, constraint, and failure modes live in each row's trade-offs, not here. First make sure every
applicable switch from the [batch checklist](#how-to-tune) is on, and check the enable conditions of the
workload-dependent switches in their rows. No universally good value exists for the knobs — the lists below say
where to start, and the rows' trade-offs say what each change costs.

### Lower decode latency (TPOT)

On MLA and DeepSeek-style MoE models, first enable the MLAPO and multistream-MoE switches from the
[batch checklist](#how-to-tune); the knobs below come after them.

1. [Speculative decoding](#speculative-algorithm) ([steps](#speculative-num-steps),
   [draft tokens](#speculative-num-draft-tokens)) — one target forward verifies several draft tokens; the payoff is
   acceptance-rate dependent.
2. [`--cuda-graph-max-bs-decode`](#cuda-graph-max-bs-decode) — remove kernel-launch overhead.
3. [`--attn-dp-size`](#attn-dp-size) — more independent decode instances.
4. [`SGLANG_SCHEDULER_SKIP_ALL_GATHER=1`](#scheduler-skip-all-gather) — further reduction, only with balanced DP load.

### Higher throughput

1. [`--attn-dp-size`](#attn-dp-size) — more independent decode instances.
2. [`--max-running-requests`](#max-running-requests) — more concurrent requests per node.
3. [`--tokenizer-worker-num`](#tokenizer-worker-num) — parallelize tokenization across worker processes.

Also consider [`--ep-size`](#ep-size) (distribute experts across devices) and
[`--mem-fraction-static`](#mem-fraction-static) (more KV cache; monitor for out-of-memory errors).

### Lower time to first token (TTFT)

1. [`--chunked-prefill-size`](#chunked-prefill-size) on mixed workloads — short requests are not delayed behind a
   single long prefill.
2. Prefix caching — leave [`--disable-radix-cache`](#disable-radix-cache) unset, so shared prompt prefixes reuse KV.
3. [`--attn-cp-size`](#attn-cp-size) for long inputs — one sequence split across devices.

### Resolve out-of-memory errors

First decide whether the hardware can hold the model at all. Get the checkpoint's total size from its download page,
or run `du -sh` on the weights directory, and compare it against your total device memory. If your cards and machines
should be able to hold the weights with room to spare, the shortage is in the memory budget rather than the hardware:
adjust [`--mem-fraction-static`](#mem-fraction-static) (up when startup reports the KV pool too small, down when
serving or graph capture runs out of memory), then address fragmentation (see the `expandable_segments:True`
allocator setting below). If the weights cannot fit the hardware, load quantized weights (see
[`--quantization modelslim`](#quantization) below) or scale out to more cards or machines (a wider
[`--tp-size`](#tp-size) or [`--ep-size`](#ep-size)).

1. Lower [`--mem-fraction-static`](#mem-fraction-static) — leave room for activations and graph buffers, at less KV
   cache and fewer concurrent requests.
2. [`--quantization modelslim`](#quantization) — W8/W4 checkpoints reduce weight memory by approximately 50%/75%, at
   a small accuracy loss.

Also consider the [`expandable_segments:True`](#pytorch-npu-alloc-conf) allocator setting, which mitigates
fragmentation. If startup instead fails with `Not enough memory … increase --mem-fraction-static`, the KV pool is too
small: see [Troubleshooting](#troubleshooting).

### Serve long contexts

1. [`--enable-prefill-cp`](#enable-prefill-cp) + [`--attn-cp-size`](#attn-cp-size) +
   [`--cp-strategy`](#cp-strategy) — shard one sequence's KV and attention across devices.
2. [`--max-prefill-tokens`](#max-prefill-tokens) — let concurrent long requests co-batch in one forward.
3. [`--chunked-prefill-size -1`](#chunked-prefill-size) on a dedicated prefill group — the entire sequence prefilled
   in one pass.

rendezvous store, the bootstrap port, and the router belong to setup, and the per-model best-practice page owns them (for

[best-practice page](/docs/hardware-platforms/ascend-npus/model-deployment/best-practices/deepseek_v3_2)). What tuning
changes on a disaggregated deployment is that every row of [Parameter Reference](#parameter-reference) can take a
different value per role. The published V3.2 configuration splits them like this:

The roles differ because their workloads differ: prefill is throughput-bound on large token counts (bulk dispatch
buffers, un-chunked batches, no graphs worth capturing), while decode is latency-bound (small graph-captured batches,
the low-latency dispatch path, deeper speculation). Both roles load the same ModelSlim W8A8 checkpoint; only the budget
each leaves for KV cache differs, which is why their memory fractions differ. Decode also sets
`SGLANG_ENABLE_OVERLAP_PLAN_STREAM=1` and `SGLANG_SCHEDULER_SKIP_ALL_GATHER=1`; both carry the preconditions documented
in [their rows](#parameter-reference).

[`DEEPEP_HCCL_BUFFSIZE`](#deepep-hccl-buffsize) and INT8 dispatch on prefill
([`--deepep-dispatcher-output-dtype`](#deepep-dispatcher-output-dtype)). The topology flags (`--nnodes`,
`--node-rank`, `--dist-init-addr`) and the network-interface variables are setup, not tuning: copy them from your
model's best-practice script, because a wrong rank or an unreachable interface hangs startup.

## Feature Compatibility

[Parameter Reference](#parameter-reference).

- **Blocked**: fails at startup, hangs, or silently produces wrong results.

| [EPLB](#enable-eplb) + topology where TP, EP, and world size are not all equal | Blocked | Migration raises `NPU EPLB migration requires TP size = EP size = WORLD size.` |
| [HCCL expansion mode](#hccl-op-expansion-mode) + `HCCL_OP_EXPANSION_MODE=AIV` on Atlas A2 systems with DeepEP | Blocked | Vendor docs report unknown-operator errors; leave it unset on that combination. |
| LoRA + [`SGLANG_ENABLE_OVERLAP_PLAN_STREAM=1`](#overlap-plan-stream) | Blocked | The speculative plan stream is incompatible with LoRA under any LoRA-compatible speculative algorithm (EAGLE/NEXTN/EAGLE3, DFLASH, DSPARK). |

The published DeepSeek V3.2 configuration — the source of the reference values — runs NPU Graph, TP, attention DP, EP,
quantization, speculative decoding, and the DP LM head together on the decode side; the per-role table above shows
most of it, and TP is `32` with both roles loading the same ModelSlim W8A8 checkpoint (see
[Parameter Reference](#parameter-reference)).

## Troubleshooting

| Symptom | Likely Cause | Fix |
| ------- | ------------ | --- |
| Startup fails with `Not enough memory. Please try to increase --mem-fraction-static.` | The KV pool computed to zero (or negative) capacity once weights were loaded | Raise [`--mem-fraction-static`](#mem-fraction-static) in small steps; if the weights alone consume the budget (e.g., BF16), the hardware is the limit — scale out or load a ModelSlim checkpoint |
| Out of memory during serving or graph capture | `--mem-fraction-static` leaves no headroom for activations or graph buffers, or the weights are BF16 | Lower [`--mem-fraction-static`](#mem-fraction-static); if the model is BF16, the hardware itself is the limit — load a ModelSlim W8A8/W4A4 checkpoint ([`--quantization modelslim`](#quantization) loads pre-quantized checkpoints only; to quantize your own with msModelSlim, see [Quantization on Ascend](/docs/hardware-platforms/ascend-npus/optimization/quantization)) or scale out |
| NPU Graph capture aborts with `Do not support TASK_QUEUE_ENABLE = 2 during NPU graph capture` | Level-2 task queue is incompatible with graph capture | Set [`TASK_QUEUE_ENABLE`](#task-queue-enable)=`0` (or `1`) on the role that captures graphs |
| NPU Graph capture aborts with an `AssertionError` whose message is `capture_bs=[]` | Every decode bucket missed the batch-size alignment, so the capture list is empty | Raise [`--cuda-graph-max-bs-decode`](#cuda-graph-max-bs-decode) to at least the alignment and to a multiple of it, or narrow the alignment by removing attention DP or the MoE all-to-all backend; see [Graph batch-size alignment](#graph-batch-size-alignment) |
| DeepEP dispatch fails at runtime | Per-rank dispatch tokens exceed the buffer | Size [`SGLANG_DEEPEP_NUM_MAX_DISPATCH_TOKENS_PER_RANK`](#deepep-dispatch-buffer) to the actual per-iteration maximum; see [Sizing the DeepEP dispatch buffer](#sizing-the-deepep-dispatch-buffer) |
| Intermittent pinned host memory allocation failures | Pinned host pool fragmentation | Append `pin_memory_expandable_segments:True` to [`PYTORCH_NPU_ALLOC_CONF`](#pytorch-npu-alloc-conf); requires CANN 8.5.0 / driver 25.5.0 or newer (the driver check is waived on Ascend 950 and newer), otherwise the setting is reset to `False` with a one-time warning |
| Expert hotspots or uneven load across NPUs | Static expert placement | [`--enable-eplb`](#enable-eplb) (requires the `deepep` backend and `TP = EP = world size`; `--ep-num-redundant-experts` adds replication) |
| Startup fails with `--cp-strategy must be set when --enable-prefill-cp is enabled.` | Prefill CP enabled without a strategy | Add [`--cp-strategy`](#cp-strategy) `interleave` for DeepSeek V3.2, or `zigzag` for MiMo V2 |
