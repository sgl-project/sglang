---
title: Diffusion language models
---
Diffusion language models have shown promise for non-autoregressive text generation with parallel decoding capabilities. Unlike auto-regressive language models, different diffusion language models require different decoding strategies.

## Example Launch Command

SGLang supports different DLLM algorithms such as `LowConfidence` and `JointThreshold`.

```bash Command
python3 -m sglang.launch_server \
  --model-path inclusionAI/LLaDA2.0-mini \ # example HF/local path
  --dllm-algorithm LowConfidence \
  --dllm-algorithm-config ./config.yaml \ # Optional. Uses the algorithm's default if not set.
  --host 0.0.0.0 \
  --port 30000
```

## First-Done-First-Out (FDFO) Scheduling

FDFO scheduling is **enabled by default**: each request leaves the batch as soon as its block is resolved, instead of advancing in lockstep where fast-converging requests must wait for slow long-tail requests before leaving the batch (head-of-line blocking). This improves throughput and is orthogonal to `--dllm-algorithm`, so it works with any dLLM algorithm. Pass `--no-dllm-fdfo` to fall back to synchronous lockstep scheduling:

```bash Command
python3 -m sglang.launch_server \
  --model-path inclusionAI/LLaDA2.0-mini \
  --dllm-algorithm LowConfidence \
  --no-dllm-fdfo \
  --host 0.0.0.0 \
  --port 30000
```

## Example Configuration File

Depending on the algorithm selected, the configuration parameters vary.

LowConfidence Config:

```yaml Config
# Confidence threshold for accepting predicted tokens
# - Higher values: More conservative, better quality but slower
# - Lower values: More aggressive, faster but potentially lower quality
# Range: 0.0 - 1.0
threshold: 0.95

# Default: 32, for LLaDA2MoeModelLM
block_size: 32
```

JointThreshold Config:

```yaml Config
# Decoding threshold for Mask-to-Token (M2T) phase
# - Higher values: More conservative, better quality but slower
# - Lower values: More aggressive, faster but potentially lower quality
# Range: 0.0 - 1.0
threshold: 0.5
# Decoding threshold for Token-to-Token (T2T) phase
# Range: 0.0 - 1.0
# Setting to 0.0 allows full editing (recommended for most cases).
edit_threshold: 0.0
# Max extra T2T steps after all masks are removed. Prevents infinite loops.
max_post_edit_steps: 16
# 2-gram repetition penalty (default 0).
# An empirical value of 3 is often sufficient to mitigate most repetitions.
penalty_lambda: 0
```

## Example Client Code Snippet

Just like other supported models, diffusion language models can be used via the REST API or Python client.

Python client example for making a generation request to the launched server:

```python Example
import sglang as sgl

def main():
    llm = sgl.Engine(model_path="inclusionAI/LLaDA2.0-mini",
                     dllm_algorithm="LowConfidence",
                     max_running_requests=1,
                     trust_remote_code=True)

    prompts = [
        "<role>SYSTEM</role>detailed thinking off<|role_end|><role>HUMAN</role> Write a brief introduction of the great wall <|role_end|><role>ASSISTANT</role>"
    ]

    sampling_params = {
        "temperature": 0,
        "max_new_tokens": 1024,
    }

    outputs = llm.generate(prompts, sampling_params)
    print(outputs)

if __name__ == '__main__':
    main()
```

Curl example for making a generation request to the launched server:

```bash Command
curl -X POST "http://127.0.0.1:30000/generate" \
     -H "Content-Type: application/json" \
     -d '{
        "text": [
            "<role>SYSTEM</role>detailed thinking off<|role_end|><role>HUMAN</role> Write the number from 1 to 128 <|role_end|><role>ASSISTANT</role>",
            "<role>SYSTEM</role>detailed thinking off<|role_end|><role>HUMAN</role> Write a brief introduction of the great wall <|role_end|><role>ASSISTANT</role>"
        ],
        "stream": true,
        "sampling_params": {
            "temperature": 0,
            "max_new_tokens": 1024
        }
    }'
```

## Forward-count metrics

The Python `/generate` API and `Engine.generate` return request-level work in
`meta_info.dllm_metrics`:

```json
{
  "forward_count": 48,
  "prompt_forward_count": 6,
  "generation_forward_count": 40,
  "recompute_forward_count": 2,
  "completion_tokens": 128,
  "tokens_per_forward": 3.2
}
```

`forward_count` counts model forwards that the request actually participates in,
including uncached prefill, denoising, final KV updates, and recomputation after
retraction. It excludes initialization and CUDA graph capture. In synchronous
batches, a completed row still counts forwards while it waits for other rows.
FDFO counts only rounds that contain the request. These are per-request counts;
summing them across requests does not give the number of GPU batch forwards.

The total is the sum of three counters:

- `prompt_forward_count`: prompt-only encoding outside previously computed regions.
- `generation_forward_count`: denoising and final KV updates, including a block
  that contains both a prompt tail and newly generated tokens. For DiffusionGemma,
  context encoding after generated blocks also belongs to generation.
- `recompute_forward_count`: committed-token prefill that replays previously
  computed positions after retraction. A context call spanning both replayed and
  new positions counts wholly as recomputation; a denoising call counts wholly
  as generation. This is a classification of calls, not a token-weighted split.

`recompute_forward_count` records replay work; it does not enable retraction.
In the validated single-GPU SDAR setup without overlap or prefill/decode
disaggregation, native decode-memory-pressure retraction does not select dLLM
requests, and retracting pauses have queue-lifecycle limitations. Recompute
accounting was tested with controlled synchronous replay using real KV release,
reset, and requeue.

`completion_tokens` matches the outer completion-token count after stop/length
truncation. `tokens_per_forward` divides it by `generation_forward_count`, or
returns `0.0` when `generation_forward_count` is zero. Prompt encoding and retraction
prefill therefore do not enter its denominator. This ratio measures generated
tokens per generation forward, not latency, throughput, or output quality.

All scalar metrics are cumulative in non-streaming, normal streaming, and
`--incremental-streaming-output` responses. Only token/text payloads are
incremental. Chunks can contain forwards without new tokens. Use the last
metrics snapshot for a request; do not sum snapshots or average their ratios.
Clients needing increments can subtract consecutive cumulative counters.

These fields are available in native Python `/generate` JSON responses and
`Engine.generate` dictionaries. A streamed batch output with an abort finish
reason can include them; a separate abort notification has no metrics snapshot.
Coalescing uses the last chunk's scalar metadata, so a final notification without
metrics does not inherit an earlier snapshot. The Rust frontend and generated
`GenerateMetaInfo` schema do not expose these fields.

For custom algorithm callers, `DllmAlgorithm.run()` now returns `DllmRunOutput`
with an added `forward_count` field. Use named fields or unpack six values instead
of five.
