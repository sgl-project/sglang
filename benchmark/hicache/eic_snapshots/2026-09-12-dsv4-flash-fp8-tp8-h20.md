# EIC benchmark snapshot: DeepSeek-V4-Flash FP8, TP8, 8×H20

2026-09-12. `cklxx/eic-patch` 13d2450b70 (PR #767) on ep_main 8ab9652e7c, image
`sglang:v0.5.19.iaas.nightly.202609101115-cu130`, node 192.168.0.53 (runs a local
EIC agent; the second agent is on 192.168.0.54).

## Environment

- GPU: 8 × NVIDIA H20, 97871 MiB, driver 535.161.08
- CPU: 192 cores on the node; pod limit 20 CPU, 600Gi memory
- EIC: `eic_trans_type: 2`, `enable_kvset_gpu_direct: False`,
  `enable_kvget_gpu_direct: True`, sync kv set, 4 MiB chunks, 3 chunks per
  256-token page (`page_bytes=9158208` per rank)

## Model

`DeepseekV4ForCausalLM`: 43 layers, hidden 4096, 64 heads, 256 routed + 1 shared
experts, top-6, `moe_intermediate_size` 2048, vocab 129280, sliding window 128,
`q_lora_rank` 1024, FP8 e4m3 weights (`scale_fmt: ue8m0`).

## Workload

Derived from the launch args: the concurrency ladder tops out at
`--max-running-requests 32`; 3500/1500 matches the team's existing serving
benchmark; the EIC case uses 16K prompts, one `--chunked-prefill-size` chunk.

```
python3 -m sglang.bench_serving --backend sglang --base-url $URL --model /model \
  --tokenizer /model --dataset-name random-ids --random-range-ratio 1 \
  --request-rate inf --warmup-requests 0 --cache-report ...
```

- A: `--random-input-len 3500 --random-output-len 1500`, concurrency 1/8/16/32,
  prompts 4/32/64/128, seed 200+concurrency. A distinct seed per step keeps an
  earlier step's EIC write-through from becoming hits.
- B: `--random-input-len 16000 --random-output-len 16 --max-concurrency 8
  --num-prompts 32 --seed 2001`, run twice. `eic_hit` replays `eic_cold`'s prompts
  after `/flush_cache`, which clears device and host but not EIC.

Each step starts with `/flush_cache`, retried until it succeeds. Flush is refused
until EIC write-through drains (see "Flush wait"). `bench_serving --flush-cache`
flushes 1 s after warmup and fails with HTTP 400 under EIC, so it is not used.

`random-ids` prompts are decoded to text and re-tokenized by the server. Server
prompt tokens run about 2.3% above the client's count, so hit rates below use the
server's `sglang:prompt_tokens_total` delta.

## B. EIC load-back (16000 in / 16 out, concurrency 8, 32 prompts, same seed)

| Run | Duration s | Input tok/s | TTFT mean / p50 / p99 ms | E2E mean ms | Cached / server prompt tokens |
|---|---|---|---|---|---|
| eic_cold | 110.1 | 4652 | 25438 / 26982 / 30596 | 27508 | 0 |
| eic_hit | 32.6 | 15692 | 7151 / 7839 / 8589 | 7244 | 519168 / 523854 (99.1%, storage) |
| baseline, EIC off | 36.1 | 14163 | 8019 / - / 11069 | 9032 | 0 |

The baseline is the number to compare against, not `eic_cold`. On this hardware
an EIC hit is roughly as fast as recomputing the prefill: 32.6 s vs 36.1 s
(-10%), input 15692 vs 14163 tok/s (+11%), mean TTFT 7.2 s vs 8.0 s (-11%). The
node difference above is worth a few points of that. `eic_hit` beats `eic_cold`
by 3.4x only because `eic_cold` pays write-through.

Read: 519168 / 256 = 2028 pages × 9158208 B = 18.6 GB per rank in 32.6 s, about
0.57 GB/s per rank and 4.6 GB/s per node, or 15.7K tokens/s. H20 prefill for this
model is 14.2K tokens/s, so L3 read and recompute are within 11% of each other.
EIC wins on prefix length and load, not on this shape.

Write-through is the bottleneck for prefill-heavy traffic: `eic_cold` took 110.1 s
against the baseline's 36.1 s (3.05x) and needed another 12.4 s to drain, so
523854 tokens took 122.5 s to write, about 4.3K tokens/s (0.16 GB/s per rank).
That ceiling is below what the GPU can prefill, so a prefill-dominated burst
queues behind it. In section A, decode hides it.

## Write-path config A/B

Why write-through is slow. Same workload as section B (32 × 16K prompts,
concurrency 8), node 192.168.0.68, one server restart per variant, a different
seed per variant so none can hit another's keys.

| Write config | Cold s | Cold input tok/s | Hit s | Hit input tok/s | Tokens in EIC | Dropped batches |
|---|---|---|---|---|---|---|
| sync, no GPU direct (shipped) | 113.8 | 4500 | 30.2 | 16963 | 519424 | - |
| `enable_kvset_gpu_direct: True` | crash | - | - | - | - | - |
| `enable_async_kvset: True`, 1 GiB pool | 77.3 | 6624 | 47.6 | 10758 | 259584 (50%) | yes |
| `enable_async_kvset: True`, 4 GiB pool | 118.0 | 4339 | 33.8 | 15165 | 519168 | 0 |

Neither knob raises write throughput.

`enable_kvset_gpu_direct: True` segfaults inside the EIC client's own IO thread,
which is why the shipped config has it off:

```
*** SIGSEGV (@0x7f4218fffff8) received by PID 13295 ***
    @ be::Engine::Transmit()
    @ be::provider::common::detail::CoreContext::DoPoll()
    @ byterpc::EventDispatcherMaster::LoopEvents()
    @ eic::client::IOHandler::Init
```

The rank's write thread dies there; the other ranks then fail in the write-path
`all_reduce` with a gloo "connection reset by peer", and the server exits. Fixing
this belongs to the EIC client, not to sglang.

`enable_async_kvset: True` queues into a write pool of
`gdr_bounce_buffer_size / chunk_bytes` slots (1 GiB / 4 MiB = 256 by default) and
drops a batch when the pool is full (`eic async write pool exhausted`). At the
default size it looked 32% faster on the cold run, but only half the tokens
reached EIC, so the replay was slower than the sync baseline. At 4 GiB (1024
slots) nothing is dropped and the cold run is no faster than sync. The 0.16 GB/s
per rank write ceiling is in the EIC path itself, not in queueing.

Under async, `/flush_cache` stops being a proxy for "data is in EIC": it returned
in 0.8 s because the batch is queued, not written.

## Flush wait (write-through drain of the previous step)

| Before step | Previous step | Wait |
|---|---|---|
| tput_c1 | none, server idle (flush round trip) | 0.76 s |
| tput_c8 | tput_c1 | 0.83 s |
| tput_c16 | tput_c8 | 2.53 s |
| tput_c32 | tput_c16 | 4.90 s |
| eic_cold | tput_c32 | 45.1 s |
| eic_hit | eic_cold | 12.4 s |

Write-through to EIC trails prefill. After the 99 s concurrency-32 step, which
prefilled 458K tokens, the backlog took another 45 s to drain.
