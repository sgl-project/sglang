# Issue 49336: SM90 decode regression v0.5.22 to v0.5.23, and DeepSelect on Hopper

Status: change prepared, not measured. No GPU was available for this work; every
number below is the reporter's, not reproduced here.

## Root cause (verified by reading code)

1. `python/sglang/srt/layers/attention/dsv4/v41_indexer/full_topk.py` (constructor,
   `FullTopKIndexer.__init__`) sets
   `use_deep_select_decode = not use_deep_gemm_decode and is_deep_select_supported()`.
2. `python/sglang/srt/layers/attention/dsv4/v41_indexer/__init__.py:87` passes
   `use_deep_gemm_decode=is_sm100_or_newer()`, and `is_sm100_or_newer()`
   (`__init__.py:54-59`) is `is_sm_at_least(10)`. On SM90 it is False.
3. `python/sglang/kernels/ops/attention/deep_select.py:82` has
   `SUPPORTED_CUDA_ARCHS = ((9, 0), (10, 0), (10, 3), (10, 7))`, and
   `is_deep_select_supported()` (`:203-206`) returns True on (9, 0).
4. Result: on SM90 `use_deep_select_decode` is always True, so `_torch_decode`
   (`full_topk.py`, around `topk_decode`) takes the `topk_page_transform`
   (DeepSelect) branch and never reaches `select_decode` (the top-k v2 path).

History:
- `b50fdeb0ef` (#41561, "Use DeepSelect for Hopper full top-k decode") introduced
  the flag. `git merge-base --is-ancestor` confirms it is in `v0.5.23` and not in
  `v0.5.22`. `v0.5.22:full_topk.py` contains no DeepSelect reference at all, so
  v0.5.22 decode on SM90 used `select_decode`.

So the reporter's A/B (DeepSelect on vs off) is consistent with the code: the flag
is the only SM90 difference in the decode indexer selection between the two tags.

## Evidence

From the issue body (reporter's measurements, unverified here):
- DeepSelect disabled on v0.5.23 image: step_ms -3 to -4%, tokens/step 3.59 to
  4.22 at 8K c12 and 3.99 to 4.66 at 64K c12, tok/s +21 to +24%.
- Residual after disabling: 26 to 35% below v0.5.22 in step_ms.

From the issue comments (reporter, unverified here):
- Comment 2 and 3 identify a host-side device-to-host readback per DSpark decode step:
  `deepseek_v4_backend.py:2215` `seq_lens.tolist()` fallback, reached because
  `dspark_components/dspark_draft.py:633` returns `draft_seq_lens_cpu = None` when
  `attn_backend.needs_cpu_seq_lens` is False, and `deepseek_v4_backend.py:1452`
  sets `needs_cpu_seq_lens = not spec_alg.is_dspark() and ...`.
- The reporter attributes the `dspark_draft.py` gate to `a9bf8c76a0` (#45925). In
  this worktree, `git show --stat a9bf8c76a0` touches `dspark_draft.py`, which
  supports the attribution, but I did not read the commit diff in full.
- Reporter states `a0d4034d5b` (#46891) and `357c53885f` (#46897) on main remove
  the host fallback. Both are in HEAD (upstream/main) and not in `v0.5.23`. In HEAD
  the gate at `dspark_draft.py:633` is still present, so I have not confirmed that
  those commits remove it in full. Treat this as the reporter's claim.

## What the evidence does not prove

- The DeepSelect A/B is one arm of a benchmark on one hardware setup (8x H20-3e,
  DSPARK, prefill CP 8). It has not been reproduced here.
- Acceptance change (tokens/step) is measured; I have not verified the mechanism.
  The code difference is ordering: DeepSelect uses `sorted_index=False` into
  `topk_page_transform`, while `select_decode` on the paged path uses top-k v2 plus
  `finish_paged_indexer_topk`, and the dense path sorts indices in `write_decode`.
  Different tie-breaking between these paths is a plausible cause of acceptance
  differences, but it is not shown. Note also the SM90 candidate cluster tier in
  `deep_select.py` (`_candidates_cluster_size`, `topk.py:229`) is an SM90 decision
  that the reporter says is bf16-only precompiled; I did not verify that.
- The residual 26 to 35% is not in the kernels per the reporter's GPU-only profile
  (total kernel time +9.6%). Candidate causes, none confirmed:
  - host-side readback per step (the `seq_lens.tolist()` path above), which the
    reporter's py-spy and trace counts support but I have not reproduced;
  - v0.5.23 control-path changes between the tags (1,010 commits). Narrowed
    candidates from the issue, all confirmed ancestors of v0.5.23 and absent from
    v0.5.22: `b50fdeb0ef` (#41561), `9d68ecce2e` (#44051, cluster top-k),
    `476fe86a12` (#45251, verify rows scored as one request), `377cd867fd`
    (#43775, k-pool indexer through top-k v2), `c82e8bd5fe` (#44210, paged score
    rows for DeepSelect decode), `a9bf8c76a0` (#45925, DSpark draft gate).
  - batch-scaling effects that are not in the DeepSelect path.

## Proposed fix and trade-off

Change: on SM90 keep `use_deep_select_decode` False, so decode uses `select_decode`
as v0.5.22 did. Implemented in `full_topk.py` as
`and not current_arch().is_sm(9)` in the `use_deep_select_decode` expression.

Trade-off:
- Reporter's data: this recovers acceptance, which is where the throughput
  gain comes from. step_ms moves only -3 to -4%, so DeepSelect itself is a
  small per-step cost on SM90 in this setup.
- DeepSelect on Hopper was added on purpose in #41561 for a performance reason.
  Disabling it may remove a step-time benefit for other shapes or batch sizes
  that the reporter did not measure. The change should be reverted or narrowed
  if a benchmark on those shapes shows a loss.
- This does not fix the 26 to 35% residual. It also does not address the host
  readback. The fix for that is the DSpark draft-path change, which is a separate
  question (see open questions).

## Other Hopper decisions on the same path (question 1 of the issue)

- `scoring.py:566` `paged = get_platform().is_sm90`: SM90 decode scores use the
  paged layout and need a top-k v2 plan (`compute_topk_plan`). Changing the flag
  to False now also turns plan computation on for SM90 (`compute_topk_plan=not
  self.use_deep_select_decode`), matching v0.5.22.
- `v41_indexer/__init__.py:116` `is_sm100()`: candidate indexer is SM100-only and
  dense blocks serve other arches including SM90. Candidate blocks on Hopper are
  not enabled (`#40860`, per the issue).
- `index_logits.py:23-42`: index logits are fp32 on SM90 and bf16 only on SM100.
  This is one of the inputs to the tie/ordering difference the issue asks about.
- `kernels/ops/attention/dsv4/topk.py:229` `_candidates_cluster_size`: SM90 and
  SM100 use the cluster top-k tier. Relevant to #44051.

  `TestDeepSelectFullTopKDecode` sets `use_deep_select_decode = False` by hand. It
  does not assert the Hopper gate. No existing test asserted that Hopper uses
  DeepSelect. `test/registered/kernels/ops/attention/test_deep_select.py` is a
  GPU test on `is_deep_select_supported()`, so it is unaffected.
- Added: `TestFullTopKDecodeDeepSelectGate` in the same file, CPU-only, which mocks
  `current_arch` and `is_deep_select_supported`. Cases: SM90 keeps select_decode;
  SM100 uses DeepSelect when supported; DeepGEMM decode or an unsupported device
  disables it.

  installed in this environment. `py_compile` passed on both edited files.
