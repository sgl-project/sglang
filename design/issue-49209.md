# Issue #49209: RTX 5080/5090 (sm_120) cannot serve with the CUDA 13 wheel install

Source: https://github.com/sgl-project/sglang/issues/49209 (fetched with `gh issue view`).
Environment in the report: RTX 5080 (sm_120) under WSL2, Ubuntu 26.04, SGLang 0.5.23,
PyTorch 2.14.1+cu130, flashinfer-python 0.7.2, nvidia-cuda-nvcc 13.5.37, nvidia-cuda-runtime 13.0.96,
no system CUDA Toolkit.

Status of this work: analysis only. Every claim below about failure causes comes from the issue text and
from reading the repo; it has not been re-run.

## Summary

A plain `uv pip install sglang` (CUDA 13 wheels) on consumer Blackwell cannot serve any model
without five manual workarounds. The README hardware table lists "RTX 30/40/50 series" with no
qualifier, and `docs/docs/hardware-platforms/nvidia-gpus.mdx` does not mention RTX or sm_120 at all.
The docs troubleshooting section covers only the source-build `CUDA_HOME` error, not the
`deep_gemm` import-time assertion.

Two root causes account for most failures:

1. **Wheel-only nvcc is not discoverable.** Several libraries resolve CUDA only from
   `CUDA_HOME` or `nvcc` on `PATH`. The nvcc in `nvidia/cu13/bin` is on neither.
2. **Two CCCL trees on one include path.** flashinfer bundles an older `libcudacxx`/CCCL under
   `flashinfer/data/cccl`. The `nvidia-cuda-nvcc` 13.x wheel ships a newer one. When both are on
   nvcc's include path, `cuda/std/__cccl/cuda_toolkit.h` hard-errors.

A third, independent problem is a hardcoded `lib64` link path in this repo (see F3).

Workaround flags that the issue reports as working, and whether they touch this repo:

- `--attention-backend triton` and `--cuda-graph-backend-prefill disabled`: real flags in this repo
  (`server_args.py`). They avoid the flashinfer prefill JIT. Documented as user workarounds only.
- `--sampling-backend pytorch`: real flag. Avoids flashinfer sampling JIT (F5).
- `CUDA_HOME`, `CC=gcc`, `LD_LIBRARY_PATH`, and the `lib64` symlinks: environment and filesystem
  workarounds for F1 and F3.

## Where sm_120 is gated in this repo

Detection helpers (`python/sglang/srt/utils/device.py`):

- `is_sm120_supported()`: capability major 12 and torch CUDA >= 12.8. Includes SM121.
- `is_sm120()`: exactly capability (12, 0). Consumer RTX Blackwell only.
- `is_sm100_supported()` and `is_sm100_or_sm110_supported()` exclude major 12 on purpose.

JIT target selection (`python/sglang/kernels/jit/utils/arch.py`):

- `_cuda_arch_suffix(12, 0)` returns `f` only when `_jit_cuda_version() >= (12, 9)`, else `a`.
  Plain `sm_120` is explicitly rejected in the docstring.
- `_jit_cuda_version()` runs `<cuda_home>/bin/nvcc --version`. `cuda_home()` in `toolchain.py`
  resolves `CUDA_HOME`, then `CUDA_PATH`, then `nvcc` on `PATH`, then `/usr/local/cuda`. On the
  reporter's machine the wheel nvcc is found only if `CUDA_HOME` is set, so the probe falls back
  to `torch.version.cuda`. That is a correctness-relevant fallback, worth a test.

Kernel and backend paths that branch on SM12x (all under `python/sglang/kernels/ops/attention/`):

- `flash_mla_sm120.py`, `flash_mla_sm120_triton.py`: sparse MLA decode, FlashInfer or Triton.
- `fa4_sm120/`, `flash_attention_v4_sm120.py`: FA4 forward.
- `fp8_fa_sm120/`: CuTe-DSL FP8 attention, needs the `a` or `f` target.
- `extend_attention.py:101`: `arch.is_sm(12)` shrinks tile sizes for 100 KB shared memory.
- `dsa/triton_sparse_mla_prefill.py`: tile table entries for (12, 0) and (12, 1).

DeepGEMM indexer gates (`python/sglang/srt/layers/attention/dsv4/v41_indexer/__init__.py`).
Commit `5e6995dd09` (#49182, after the reporter's SGLang 0.5.23 base) split them:

- `is_sm100()`: strict SM100. Gates the candidate/sparse-table path. Keeps SM120 out because
  DeepGEMM's sparse mqa-logits kernels assert arch == 10 (#49173).
- `is_sm100_or_newer()`: used for dense prefill and decode DeepGEMM indexers, so SM120 uses them.

Prior sm_120 history: `403b855a22` "Add sm_120 for blackwell (#5903)", `f8f501f2e8` NVFP4
diffusion on sm_120. These are the commits that introduced the current gating style.

Documentation: README line 55 lists "RTX 30/40/50 series". The install guide
(`docs/docs/get-started/install.mdx`) has a `CUDA_HOME` troubleshooting entry that covers only
`OSError: CUDA_HOME environment variable is not set` from source builds. It does not mention the
`deep_gemm` assertion, the `nvidia/cu13` layout, or the CCCL conflict.

Packaging: `python/pyproject.toml` pins `flashinfer_python[cu13]==0.7.3`,
`nvidia-cutlass-dsl[cu13]==4.8.0`, `sgl-deep-gemm==0.2.7`. The issue reports flashinfer 0.7.2
at the time, so the reporter's stack is one minor version behind the pins. Whether 0.7.3 fixes the
CCCL bundling is not verified.

`python/sglang/check_env.py` reports `torch.utils.cpp_extension.CUDA_HOME`, which is None on a
wheel-only install. It does not look at the wheel nvcc, so `check_env` gives a misleading picture
for this setup.

## What belongs in this repo

Candidate changes, ordered by confidence:

1. **F3 (lib64 link path). Already in progress by another contributor.** The fix belongs in
   `toolchain.py` (`base_link_flags`, `cuda_stubs_dir`). Pick `lib64` or `lib` under `cuda_home()`
   and fall back to `-l:libcudart.so.<N>`. Let the open PR land. Not done here.
2. **Make `check_env` and the install docs show the wheel-nvcc case.** Report the resolved nvcc
   and `CUDA_HOME` from `toolchain.cuda_home()` instead of only torch's value. Document the
   `CUDA_HOME` requirement for `deep_gemm` on wheel-only installs, and the flags from the issue as a
   known-issue table for RTX 50-series.
3. **Launcher-side default for `CUDA_HOME` (needs maintainer decision).** If `CUDA_HOME` is unset
   and an nvcc exists at `<site-packages>/nvidia/cu13/bin/nvcc`, set `CUDA_HOME` to that root
   before `deep_gemm` imports. This is a process-global environment side effect, and the
   maintainers should approve it. It is the cleanest fix for F1 in this repo. Not made here
   because it changes process env on import for every user.
4. **F4 include order.** Check the JIT include list for the sm_120 FP8 kernel. Make sure the
   toolkit's CCCL comes before any flashinfer-bundled CCCL. Needs a full toolkit build to verify and is a
   small code change.
5. **Docs.** A RTX 50-series subsection in `nvidia-gpus.mdx` that states which flags are needed
   on wheel-only installs until the upstream fixes land. Only after the upstream state is known.

## What belongs upstream

- **deep_gemm** (`sgl-deep-gemm`): `find_cuda_home()` should fall back to nvcc in the installed
  `nvidia/cu*` package, or raise a clear error with the path to set.
- **flashinfer**: stop bundling a CCCL that conflicts with nvcc 13.x, or guard `cuda_toolkit.h`
  so the same-version check passes. Affects F2 and F5, and F4 through the CUTLASS include.
- **nvidia-cuda-nvcc / nvidia-cuda-runtime wheels**: consistent `lib` vs `lib64` layout, or
  a documented search path. Affects F3 for any downstream build.

## Test plan

CPU-only (runnable without a GPU, suitable for this repo's unit-test tier):

- `cuda_home()` resolution: `CUDA_HOME` wins, then `CUDA_PATH`, then `nvcc` on `PATH` (mock
  `shutil.which`), then `/usr/local/cuda`. Use a temp directory with a fake `bin/nvcc`.
- `_cuda_arch_suffix(12, 0)`: returns `f` for JIT CUDA >= 12.9, `a` for 12.8 and for the
  torch-version fallback. Returns `a` for (12, 1). Mock `_jit_cuda_version`.
- `base_link_flags` for `lib`-only and `lib64` layouts (overlaps with the open F3 PR; coordinate).
- `is_sm120()`, `is_sm100_or_newer()`, `is_sm100()` truth tables for capabilities (9,0), (10,0),
  (12,0), (12,1) with mocked `current_arch()`.

GPU:

- Fresh venv, `uv pip install --prerelease=allow sglang`, no `CUDA_HOME`, `Qwen/Qwen3-4B` BF16,
  default backends. Expect F1 to reproduce.
- Repeat with the workaround set from the issue, one flag at a time, to confirm which of F2 to F5
  each flag clears.
- FP8 model (`Qwen/Qwen3-8B-FP8`) with and without the F4 include-order change.
- Confirm the `_jit_cuda_version()` result and the `-gencode` flag that the JIT build emits.

## Open questions

1. Is the wheel-only install (no system CUDA Toolkit) a supported configuration for SM120? The
   issue asks this directly, and the README does not say. The answer decides whether the fix is
   in code or in docs.
2. Should SGLang set `CUDA_HOME` itself from the wheel nvcc, or should that stay with deep_gemm?
3. Does flashinfer 0.7.3 (the pinned version) still bundle the conflicting CCCL? The issue used
   0.7.2.
4. Does the torch-version fallback in `_jit_cuda_version()` select a target that the wheel nvcc
   accepts? For a cu13 wheel with `torch.version.cuda` 13.0, the suffix is `a`, which is fine,
   but that should be confirmed on hardware.
5. Related issues #14814 and #9140 concern `trtllm_mha` on sm_120. Are they still open, and do
   they affect the attention backend choice for this report?
