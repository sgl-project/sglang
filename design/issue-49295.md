# Issue #49295: breakable prefill CUDA graph returns wrong, non-repeatable prompt logprobs for short prompts

Status: analysis only. No GPU is available in this environment, so nothing below is a measurement. All numbers quoted are from the issue reporter. Line numbers refer to this worktree (branch `design/sglang-49295`, based on upstream/main).

## Summary

On `nvidia/Qwen3.8-2.4T-A95B-NVFP4`, TP8, B300 (SM103), the default breakable prefill CUDA graph (BCG) gives prompt logprobs that differ from eager by up to 18 nat for prompts that land in the 4, 8, 16 and 32 token capture buckets. The same prompt on the same server also returns different values between runs (up to 2.8 nat in bucket 4, 8 nat in bucket 32). Eager is bit-stable. The error is concentrated on the first positions of the prompt.

Two properties matter for root cause:

1. Non-repeatability. Padding is deterministic (`input_ids`, `positions`, `out_cache_loc` are zeroed on every replay, see below). Deterministic inputs should give deterministic outputs, so some input to the replayed segments must be stale, uninitialized, or taken from a previous request.
2. Locality. Errors sit on the first 1 to 3 positions. A causal model's output at position 0 does not depend on later tokens unless something couples rows (per-tensor quantization scale, shared state, or a kernel that reads a stale window).

Per the reporter, the failing buckets are the power-of-two buckets (4, 8, 16, 32). Buckets 12, 20, 24 and 28 are clean for the 9-12 and 17-28 token ranges. Qwen3.5-397B at TP4 with triton attention does not reproduce.

## Code path (what the runner does for a short prompt)

- Bucket choice. `get_prefill_num_tokens_to_capture` (`prefill_cuda_graph_runner.py:198-204`) builds the bucket list. `_pad_to_bucket` (`base_cuda_graph_runner.py:184`) rounds up to the smallest bucket. `can_replay_locally` (`prefill_cuda_graph_runner.py:1436`) admits the batch when `padded <= 2 * num_tokens` (lines 1533-1535, `_MAX_PREFILL_CUDA_GRAPH_PADDING_FACTOR = 2` at line 194). A 2-token prompt goes to bucket 4 and replays with 2 padded rows.
- Capture shape. `capture_prepare` (line 1648) captures a bucket as the fewest synthetic requests, so bucket 4 is one request of length 4. Replay later uses live lengths (2) against the bucket-4 graph.
- Padding of static inputs. `load_batch` (line 1965) calls `buffer_registry.fill_from`. `input_ids`, `positions`, `out_cache_loc` use `PaddingPolicy.ZERO` (`cuda_graph_buffer_registry.py:943-955`), so padded rows get token 0, position 0, cache slot 0. Slot 0 is reserved (`memory_pool.py:422` starts `free_slots` at 1), so padded KV writes are harmless. This is a ruled-out path for the cross-request leak.
- Attention metadata at replay. For backends without captured metadata, `_prepare_forward_metadata_for_replay` calls `attn_backend.init_forward_metadata(forward_batch)` on the raw (unpadded) batch (line 1414), while q/k/v and the output are padded to the bucket. Attention is a break outside the captured segments, so this is the live path.
- Attention output padding. `RadixAttention` zeroes the padded tail of the attention output (`radix_attention.py:250`, `graph_utils.py:33-35`), gated by `should_zero_prefill_padding` (`runner_utils/prefill_graph.py:43-45`, set at `prefill_cuda_graph_runner.py:871-874`). This covers standard attention only.
- Linear attention (GDN) padding. `radix_linear_attention.py:125-135` trims to `global_num_token_non_padded_cpu` only on one path, and `:206` zeroes `output[:, real_num_tokens:]` only on the eager/backend-call path. The in-graph extend (`_linear_extend_in_graph`, `radix_linear_attention.py:~205-220`) instead runs the captured kernels over fixed grids (`gdn_prefill_graph.py:1-30`). Its docstring says padded rows "point past their sequence or carry PAD_SLOT_ID and return". That claim is what this issue appears to break.
- Logits tail. The eager tail (`_execute_body_capture`, line 2316, `tail_batch = static_forward_batch` at line 2370) runs `logits_processor` on the padded batch. Prompt-logprob rows are selected from cumulative raw `extend_seq_lens` (`logits_processor.py:949-1076`). Padding is at the end of the flat buffer, so the row mapping for real tokens is correct. This path is ruled out for the first-position error.
- Trimming. `_trim_logits_output` (line 2421) slices hidden states and logits to raw counts. Input token logprobs come from the logits tail and are not sliced, which is correct as long as the selected rows are real.

## Root cause hypotheses (ranked)

H1. Stale conv1d / recurrent state read by the captured GDN extend for short sequences (most likely).
- Evidence: the reporter sees the largest error in the first positions. A causal conv1d of width 4 (typical for GDN) reads the initial conv state for positions 0 to 2, which is exactly where the error sits. Prefix length is 0 after the flush, so the initial state must be zero.
- The captured extend takes `has_initial_state` and `track_dst` from static per-bucket tables (`gdn_prefill_graph.py:134-135`) rebuilt in `fill`. Any sentinel or padded sequence slot whose entry is not reset (rows bs..max_seqs) could leak prior state. Sentinel handling for padded sequences is not visible in the diff I read; this needs checking in the `fill` implementation.
- Non-repeatability fits: the state slot is reused from a previous request.
- Verification needed: GPU run with a prefix-free 2-token prompt, dump the conv state and `has_initial_state` at replay versus eager.

H2. Padded rows change a per-tensor quantity used by real rows (NVFP4 dynamic activation scale).
- Evidence: `_zero_padded_tail` (line 871) says per-tensor dynamic activation quantization reads padded rows (amax over all rows). Padded rows are zero attention output plus token-0 embedding, so they are deterministic. The M-dependence then gives a deterministic offset versus eager, which matches the reporter's "1 to 2 nat" class. It does not explain run-to-run changes by itself.
- Non-repeatability would need the padded hidden rows to differ across runs, for example from the GDN output rows (H1/H3) or from uninitialized graph-pool memory in an unzeroed path. The GDN output zeroing at `radix_linear_attention.py:206` is not reached in-graph, so this is plausible as a second mechanism.
- Verification: compare eager with replay after zeroing padded rows of every layer's input, or pad with the bucket's own token instead of 0.

H3. Capture-time metadata (one request of bucket length) mismatched with replay-time metadata (live length) inside the captured GDN and MoE segments.
- Evidence: capture uses `capture_seq_lens = [num_tokens]` (line 1648). Replay refreshes only out-of-graph metadata (line 1414 and `_prepare_forward_metadata_for_replay`). Any captured kernel that reads cu_seqlens or chunk indices from its capture-time values would see a length-4 sequence for a length-2 request.
- Power-of-two pattern is consistent with a kernel whose grid or tiling depends on bucket size. Not confirmed.

H4. Bucket-size-dependent kernel specialization (Triton integer specialization or tile sizes keyed on bucket size).
- Evidence: failures at 4/8/16/32 but not 12/20/24/28. This is a lead only. I did not identify the specialized kernel from the code I read.

H5. Padded rows of the input-embedding slot. `_fill_input_embeds_slot` (line 2283) writes only the live prefix, and `fill_from` zeros the padded region before it. Looks correct, ruled out for now unless `is_multimodal` is true for Qwen3.8 (then the slot exists and the order matters).

H6. Output row mapping and logprob shifting. Ruled out (see Logits tail above).

## Proposed fix

No code change in this commit. The bug is not localized to a line with enough confidence to make a small, correct change. The reporter's own data show that an exact-bucket replay (no padding) matches eager, so the safe mitigation is:

1. Mitigation (small, low risk): for GDN models on SM100/SM103, require `padded_num_tokens == num_tokens` in `can_replay_locally` (`prefill_cuda_graph_runner.py:1533-1535`) for the in-graph GDN extend, or cap the padding factor to 1 for buckets below 64. This trades prefill speed for correctness on short prompts, which matches the exact-bucket guard in #49613.
2. Root cause (needs GPU): instrument the in-graph GDN extend for a 2-token prompt. Compare conv state, `has_initial_state`, and per-layer outputs for rows 0 to 2 between eager and replay across two runs. Confirm or reject H1 first, then H2.
3. Fix H1 if confirmed: make `fill` reset `has_initial_state` and conv-state slots for rows `bs..max_seqs`, and route padded tokens to `PAD_SLOT_ID`.

## Test plan

- Unit (CPU): extend the buffer-registry padding tests to cover the GDN `has_initial_state` and track tables for `bs < max_seqs`. Assert that sentinel rows are reset on every `fill`.
- Unit (GPU, not run here): exact-bucket versus padded replay for a 2-token GDN extend must be bit-identical in the first 3 positions (`torch.equal`). Repeat with a long unrelated request in between to expose stale state.
- Integration (GPU, not run here): the reporter's two-prompt script, eager versus breakable, two passes, bucket 4/8/16/32 plus a 12-token control. Expect max difference under 0.05 nat in the first positions. Use the `kl-consistency-test` helper to separate batch-invariance from path differences.
- Regression: `nvidia/Qwen3.5-397B-A17B-NVFP4-V2` at TP4 (already clean) as a control.

## Overlap with #49133 and PR #49613

- #49133 reports breakable-versus-eager drift on `Qwen3.8-27B-NVFP4` caused by the GDN gate projection `in_proj_ba` changing tile reduction with M. The reporter there does not claim same-server non-repeatability.
- PR #49613 (`Closes #49133`) makes `in_proj_ba` batch-invariant on EXTEND/MIXED via `_matmul_persistent_triton`. It also keeps padded BCG replay enabled on SM100/SM103 quantized GDN models and requires an exact bucket only on other architectures or quantizations. I read the PR description only, not its diff.
- Consequence for #49295: #49613 keeps padded replay on B300 (SM103), which is the exact configuration in #49295. As described, #49613 would not remove the failure on the reporter's hardware. Its own verification is on A100 only and states that end-to-end SM103 serving was not run. Its claim that the in_proj_ba change "eliminates the padded-replay mismatch across all buckets" on SM100/SM103 is untested and should be checked against #49295 before it is accepted.
- #49613 does not address the non-repeatable or first-position symptom, which is a stale-state or padded-row problem (H1/H2), not a GEMM M-dependence problem (the issue's own analysis, and the reporter's note that the error is not a 1 to 2 nat drift).
- The two issues therefore need separate fixes. #49613 may cover the M-dependence part of #49133. #49295 needs the GDN extend padding path checked.
