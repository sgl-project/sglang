# Design: FA3 SM90 FP8 two-level accumulation slows paged head_dim=256 prefill (issue #49541)

Status: investigation and proposal. No code change.All performance and numerical numbers come from the issue report.

## Summary

- The FP8 two-level accumulation fix (sgl-flash-attn PR #51, commit `141fa063`, derived from vllm-project/flash-attention PR #104) was pulled into SGLang by #46770 (merge commit `b960aa903a`, 2026-10-28).
- In this checkout the FA3 pin is already `141fa063` (the fixed source). So current main ships the fix, and the regression applies to any sglang-kernel build made from this tree.
- The issue reports that, for SM90 paged FP8 prefill with head_dim=256, page_size=8, and 12Q:2KV, the fixed build is about 2.6x slower than the pre-fix build at long Q and KV. Short-Q, long-KV shapes are 1.3x to 2.0x slower. The regression is in the FA3 kernel, not in SGLang's Python dispatch.
- The fix adds a full copy of the O accumulator fragment and a full add-back around each accumulating FP8 GEMM. At head_dim=256 that is about 128 extra FP32 registers per consumer thread (derived; see below). The issue's evidence (register pressure, stack spill, serialized WGMMA warning C7514) fits this mechanism. It has not been isolated by measurement.
- The fix cannot simply be removed without reintroducing the long-KV numerical bias that #46770 corrected. Any change is a trade-off between accuracy and prefill throughput, and the choice belongs to maintainers.

## Root cause

### What SGLang pins (verified in this checkout)

- `python/sglang/kernels/aot/CMakeLists.txt:75-81`: `FetchContent_Declare(repo-flash-attention ... sgl-attn/archive/141fa063d57c27d77af3aa8adf1b69330dc2bc10.tar.gz, URL_HASH SHA256=16d797e0...)`. The previous pin was `f89bc230` (set by `c32c4ef79c`, the move of sgl-kernel under `sglang.kernels.aot`). `b960aa903a` changed that line.
- `python/sglang/kernels/aot/CMakeLists.txt:423-425`: the FP8 instantiation sources are globbed from `hopper/instantiations/flash_fwd_hdim[0-9]*_e4m3*_sm90.cu` and `flash_fwd_hdimdiff_e4m3*_sm90.cu`. So the head_dim=256 FP8 instantiation is compiled from the same header change as every other FP8 head dimension.
- `python/sglang/kernels/aot/CMakeLists.txt:355-361`: the only existing `FLASHATTENTION_DISABLE_*` compile definitions. `FLASHATTENTION_DISABLE_FP8_TWO_LEVEL_ACCUMULATION` (the macro that guards the fix in the upstream header) is not set or referenced anywhere in this repo.

### What changed upstream (verified via `gh api`, read-only)

- sgl-project/sgl-attn commit `141fa063` ("Add two-level accumulation for SM90 FP8 forward (#51)") changes only `hopper/utils.h`, +26 lines, in the templated `gemm()` helper. This matches the issue's claim that the two archives differ only in that file.
- The change is inside `#ifndef FLASHATTENTION_DISABLE_FP8_TWO_LEVEL_ACCUMULATION`. For each call with `Is_FP8 && !zero_init` it:
  1. copies the entire accumulator fragment `tCrC` into `tCrC_original` (`make_fragment_like`);
  2. clears `tCrC`;
  3. runs the WGMMA sequence into the cleared fragment;
  4. adds `tCrC_original` back to `tCrC` element by element.
- Inference (not checked against the mainloop source): `zero_init=false` is the accumulating P@V GEMM. The zero-init Q@K GEMM is then unaffected. This should be confirmed in `hopper/mainloop_fwd_sm90_tma_gmma_ws.hpp` in sgl-attn.
- vllm-project/flash-attention PR #104 (the upstream origin, read via `gh pr view`) touches `hopper/setup.py` (+2) and `hopper/utils.h` (+24). I did not read the setup.py toggle in detail, so I cannot say whether it is equivalent to the SGLang macro.

### Why head_dim=256 specifically (derived, not measured)

- The issue's table shows the FP8 tile `128x128x256` with 384 threads (one producer warpgroup, two consumer warpgroups). Each consumer thread holds a 64-row slice of O. Per thread that is `64 * 256 / 128 = 128` FP32 accumulator registers. For head_dim=128 it is 64.
- The fix duplicates that fragment. At head_dim=256 it needs about 256 live FP32 registers for O plus other state. The build reports 168 registers per thread for the fixed build and 32 bytes of stack for the old build versus 360 bytes for the fixed one. Those numbers are consistent with spilling against the consumer register budget (up to 240 under `setmaxnreg`, which is an assumption about the kernel's configuration).
- At head_dim=128 the same copy needs about 128 registers total for O, which fits. That would explain why the regression is reported at head_dim=256 and not at smaller head dimensions. This has not been tested.

### Why the slowdown scales with KV length

- Static instruction counts in the issue: FADD 196 to 452, LDL 13 to 156, STL 11 to 153. Executed instructions rise about 1.6x (16.6e9 to 26.8e9).
- Tensor-pipe activity falls from 55% to 21%, and `ptxas` emits C7514 (WGMMA serialized because non-WGMMA instructions read accumulator registers inside the pipeline stage). The clear and add-back sit on the critical path of every accumulating GEMM, so the WGMMA pipeline is no longer overlapped.
- Both costs are per KV iteration, so the ratio is roughly constant once there are enough KV tiles (2.6x at Q=16384 for KV 16K, 64K and 256K). With only 7 query tokens the kernel is latency-bound and the ratio is smaller.

### Ruled in or out by the repo

- The Python wrapper `python/sglang/kernels/aot/python/sgl_kernel/flash_attn.py` (`flash_attn_with_kvcache` at line 36; `num_splits=0` default at line 63; page table passed through at line 245) is a thin call into the compiled op. It does not change the kernel's accumulation. It is not the cause.
- `python/sglang/srt/layers/attention/flashattention_backend.py` routes head_dim above 256 to FA4 (`fa3_upgrades_to_fa4`, lines 313-314). Head_dim 256 stays on FA3, and FA4 on SM90 can also read an FP8 e4m3 cache at head_dim 256 (`fa4_casts_fp8_kv`, lines 323-340). That gives a possible routing alternative, see the proposal.
- The public `sglang-kernel==0.4.10` wheel: the version bump is `4cca7fcd3e` (2026-10-15), which predates `b960aa903a` (2026-10-28). The wheel therefore most likely carries the old pin. This matches the issue's measurement (output mean 0.234, same as the old rebuild). This is an inference from commit dates, not from the wheel's contents. It also means users on 0.4.10 have the numerical bias, and users on the next release from this tree get the slowdown.

## Validation plan

- The FA3 pin (`141fa063`) and its archive hash in `CMakeLists.txt:75-81`.
- That `141fa063` changes only `hopper/utils.h` relative to `f89bc230` (from the upstream commit diff, via `gh api`).
- The FP8 source globs and the absence of any `FLASHATTENTION_DISABLE_FP8_TWO_LEVEL_ACCUMULATION` setting in this repo.
- The commit ordering of the 0.4.10 bump and #46770.

Open items:
- The 2.6x timings, the cold-L2 method, and the numerical results. Those come only from the issue's reporter, who says they used a standalone rebuild, not a full SGLang server.
- The register and spill counts, C7514, and the instruction counts for this repo's build. Confirming them needs `cuobjdump -res-usage` and `ptxas -v` on the `flash_fwd_hdim256_e4m3*_sm90.cu` objects.
- Whether the mainloop applies two-level accumulation only to P@V (`zero_init=false`).
- The head_dim=128 comparison, which would test the register-pressure hypothesis.
- Whether the public wheel's pin really is `f89bc230` (requires inspecting the wheel's build or the artifact).
- Whether any production SGLang model uses FA3 FP8 paged KV at head_dim=256 on the path hit by this regression.

No benchmark or measurement is claimed in this document.

## Proposed fix options

Option A: Gate the fix off for FP8 head_dim=256 in the FA3 build.
- Change: in `CMakeLists.txt` near line 423, compile the head_dim=256 e4m3 instantiations with `-DFLASHATTENTION_DISABLE_FP8_TWO_LEVEL_ACCUMULATION` (per-source compile options), leaving other head dimensions on the fixed path. The macro already exists upstream.
- Pros: small, local to the build file, easy to revert, restores the old timing for hdim256.
- Cons: reintroduces the long-KV bias for head_dim=256 FP8, which #46770 fixed. Only acceptable if maintainers judge that hdim256 FP8 prefill accuracy at long KV is not needed, or if a precision-safe alternative is available for that shape. The compile-time gate also means no runtime toggle.

Option B: Keep the fix everywhere and route head_dim=256 FP8 paged traffic to FA4 on SM90.
- Change: in `flashattention_backend.py`, select `fa_impl_ver=4` for FP8 KV at head_dim 256 (the path already exists for `fa4_casts_fp8_kv`, lines 323-340).
- Pros: no kernel change, keeps accuracy fix.
- Cons: changes the kernel, the Q/K/V dtype path (FA4 casts K/V in-kernel with unquantized Q), and performance on SM90 is unknown. Needs accuracy and perf validation on H100. Behaviour for the paged path would need a separate review.

Option C: Change the rebuild so it does not duplicate the full O fragment.
- Candidates: promote to the FP32 total every k-block or every WGMMA atom rather than per full GEMM call, so the temporary is smaller; or stage the running total in shared memory. Both are kernel work in sgl-attn, not in this repo.
- Pros: keeps the numerical fix and removes the register cost.
- Cons: non-trivial CUTLASS/CuTe work, risk of new serialization, needs NCU and ptxas checks on every head dimension. Not something to land without full operator-level validation.

Option D: Change the tile configuration for head_dim=256 FP8 (smaller O per thread, for example a 64-row tile or a different consumer layout).
- Pros: the copy fits the register budget. The kernel stays structurally the same.
- Cons: changes the tuned performance for all FP8 hdim256 workloads, which may slow the non-regressed shapes. Needs a full benchmark sweep.

Option E: Revert the pin to `f89bc230`.
- Pros: restores the timing. Trivial to do.
- Cons: restores the long-KV bias fixed by #46770. Not recommended unless maintainers decide accuracy is not a blocker.

Option F: Ship the fix, document the regression, and track a follow-up.
- Pros: no code risk, keeps the correction.
- Cons: users of paged hdim256 FP8 prefill see a 2.6x slowdown until a follow-up lands.

Recommendation from this investigation: do not change code here. The best next step is to measure register and spill counts for the hdim256 e4m3 objects (cheap, no benchmark needed) and to decide with maintainers between A (short-term, accuracy trade-off) and B/C/D.

## Test plan

1. Reproduce with the issue's `build_pair.py` and `repro_fp8_fa3.py` (both pinned to the same FA3 commits and flags). Run fresh processes per variant, alternating order, at least three repeats. Include head_dim=128 as a control in the same harness so the register-pressure hypothesis can be tested.
2. Record `ptxas -v` and `cuobjdump -res-usage` for the hdim256 e4m3 objects built from `141fa063` and `f89bc230`, plus the C7514 warning count.
3. Accuracy: run `python/sglang/kernels/aot/tests/test_flash_attention.py` with FP8 enabled (the FP8 parametrization is at line 471). Add a long-KV V=1 check (ideal output 1) for hdim256 paged FP8 so every option can be compared on the accuracy axis as well as the speed axis.
4. For each option (A, B, C, D), measure the speed-accuracy point on the same shapes: Q in {7, 16384}, KV in {16384, 65536, 262144}.
5. For option B, run the FA4 path through `flashattention_backend.py` on SM90 with FP8 KV at head_dim 256 and confirm accuracy and perf against the FA3 fixed build.
6. End-to-end: a serving benchmark on a model that uses FA3 FP8 KV at head_dim 256, only after the operator-level results justify it.
7. Keep the numerical regression check for the fixed build (the bias #46770 fixed) as a required gate for any option that changes accumulation.

## Open questions for maintainers

1. Which production models use FA3 with FP8 KV and head_dim=256 on paged prefill? That decides how much the 2.6x matters in practice.
2. Is the long-KV bias fixed by #46770 acceptable to reintroduce for hdim256 FP8 (option A), or is accuracy a hard requirement?
3. Should head_dim=256 FP8 move to FA4 on SM90 (option B), given the existing `fa4_casts_fp8_kv` path, and has that path been validated for accuracy?
4. Is the next sglang-kernel release planned with `141fa063`? The 0.4.10 wheel appears to predate the fix (commit dates), so the decision affects that release.
5. Does vllm-project/flash-attention PR #104's `hopper/setup.py` toggle offer a per-instantiation switch we can reuse, or does it only disable globally?
6. Can the maintainers confirm whether the public 0.4.10 wheel's `flash_ops` was built from `f89bc230`? That would confirm the inference in the Root cause section.
7. Is the q=7 decode-like shape (up to 2.0x at KV 262K) on any production path? If so, that is a separate concern from prefill.
