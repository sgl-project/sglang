## 2026-11-14 · Pre-run: scope, hardware, feasibility

### Allocation and the first real finding

The practice allocation was reported as:

- `昇腾 950PR，【SGLangMeetup】sglang-950_26.2，4NPU 256G内存 64核CPU 500G存储`
- alternatively `昇腾 A2，【SGLangMeetup】sglang-A2_26.2，4NPU 256G内存 64核CPU 500G存储`
- status at the time: **compute allocation still blocked** (`our computing capacity is still blocked`)

Feasibility analysis before touching the machine ✅(docs) / 🧠(arithmetic):

| Slice | Device HBM | Ascend-validated W8A8 checkpoint (~300 GB) | Native FP4+FP8 checkpoint (159.6 GB) |
| --- | --- | --- | --- |
| 950PR/DT × 4 | chip-dependent | fits only if total HBM ≥ ~360 GB | runs only on 950 (MXFP8/MXFP4) |
| A2 × 4 | 4 × 64 GB = 256 GB | **does not fit** | **does not run** (A2 has no MXFP8/MXFP4) |
| A2 × 8 / A3 × 4 cards (8 dies) | 512 GB | fits (`--tp-size 8`) | does not run |

❌ **Decision: a 4×A2 slice cannot serve DeepSeek-V4-Flash**, for two independent reasons (capacity and
precision support). The correct action is not to retry with smaller `--mem-fraction-static`; it is to
request a different slice or a different model. Exact request text is printed by
`env/00_common.sh` so it can be pasted into the meetup group.

## Source audit — corrections applied after reading the branch head

A verification pass over the branch sources changed five things in the package. Each is the kind of detail
that silently wastes a lab slot:

1. `export ASCEND_USE_FIA=1` is **required** on 950PR/DT and was missing → added to the launch env.
2. **4-die feasibility math**: the W8A8+MTP checkpoint is 300.1 GB, so 4 dies need ≥ ~96 GB/die (75 GB/die
   is weights alone). `env/00_common.sh` now states this explicitly instead of a generic "need 380 GB".
3. **Context cap**: the model's ceiling is 1,048,576 tokens, which would OOM the KV pool on a small slice →
   the launch now passes `--context-length 131072` by default (override with `CONTEXT_LEN`).
4. **Checkpoint trap**: `Eco-Tech/DeepSeek-V4-Flash-w8a8-mtp` ships without an `encoding/` directory, and V4
   has no Jinja chat template → `/v1/chat/completions` may return 400. The weights script prints the fix
   (fetch `encoding/` from the native repo, or use `/generate`). The native 159.6 GB FP4 checkpoint fails on
   A2/A3 with "Unexpected type fp8" and is not a workaround.
5. **Metrics are off by default**: `collect_telemetry.sh` needs the server started with `--enable-metrics`,
   now included in the launch command.

Also recorded: the reasoning parser registered in this build is `--reasoning-parser deepseek-v4`
(opt-in via `ENABLE_REASONING_PARSER=1` after a baseline launch works); `--attention-backend dsv4` is the
right backend even though `support_features.mdx` still lists only `ascend`.

## Derived estimates for sanity-checking (not measurements)

- KV cache ≈ **5,940 B/token** at BF16 KV (≈3,671 B if FP8-packed KV), plus ≈3.2 MB/request for SWA state.
- Realistic single-stream TPOT: **A2 ≈ 12–25 ms**, **950PR/DT ≈ 6–12 ms**; roofline floors are 1.86–3.72 ms
  and 0.5–2.05 ms respectively, the gap being MoE all-to-all.
- On a 512 GB 8-die node: ~164 concurrent 32k-context requests at W8A8 (~×8 with DP attention); ~5 if all
  contexts are 1M.

These came from reading `deepseek_v4_memory_pool.py` / `deepseek_v4.py` on the branch and a roofline
argument, and are labelled as derived in `docs/measurements.md`.

### Late check against the support matrix (confirms the finding)

`reference/support_models.mdx` lists `Eco-Tech/DeepSeek-V4-Flash-w8a8-mtp` as supported on **both A2 and A3
Series** — so the 4×A2 blocker is purely the size of the slice (256 GB), not a missing A2 port. The only
smaller DeepSeek-V4 checkpoints in the matrix are `Eco-Tech/DeepSeek-V4-Pro-w4a8-mtp`, and V4-Pro is the
1.6T model, i.e. larger in total despite the 4-bit format. Conclusion unchanged: 4×A2 cannot host V4-Flash;
A2 × 8 or 950PR/DT × 4 (>= 96 GB/die) are the two workable asks.

### The failure chain, in the order it appeared

1. **`ValueError: Unexpected UE8M0 scale shape: got (8, 8, 32), expected (64, 32)`**
   `fp8.py → w8a8_mxfp8.py::_layout_npu_arch35_ue8m0_weights`. DeepSeek-V4's grouped `wo_a` stores block
   scales as `[G=8, N/128, K/128]`; the 950 MXFP8 re-layout expects the flattened 2-D block grid. Same
   values, same order — the routine simply never reshapes before validating.
   **Fix applied:** insert a flatten before the shape check
   (`if numel matches expected and shape differs: checkpoint_scale = checkpoint_scale.reshape(expected)`).
   ✅ Validated: weight loading then completed (48/48 shards, ~12 s).
2. **`aclnnKvQuantSparseAttnSharedkvMetadata … not in libopapi.so, or libopapi.so not found`**
   The DSv4 sparse-attention KV-metadata op exists in the image under
   `/usr/local/Ascend/cann-9.1.0/opp/vendors/custom_transformer/op_api/lib/libcust_opapi.so`, but that
   vendor was not on the op path. The A3 launch recipe sources `opp/vendors/custom_transformer/bin/set_env.bash`
   (and `customize`); the container's `.bashrc` sources neither.
   **Fix applied:** source the vendor `set_env.bash` scripts and prepend the vendor dirs to
   `ASCEND_CUSTOM_OPP_PATH`. ✅ Validated: the error disappears from the log.
3. **Decode graph capture crash** (`decode_cuda_graph_runner → npu_cudagraph_backend → deepseek_v4.py:5107`).
   **Workaround:** `--disable-cuda-graph` (eager decode; valid numbers, higher per-step overhead — must be
   stated in the report). Graph mode for DSv4 on 950 is an open item.
4. **`ModuleNotFoundError: No module named 'tilelang'`** from `sglang/kernels/ops/layernorm/mhc.py::_load_tilelang`
   — DSv4 mHC layernorm kernels attempt a lazy `tilelang` import; the image does not ship it.
   **Fix applied:** the vendor-validated switch `SGLANG_OPT_USE_TILELANG_MHC_PRE=False` and
   `SGLANG_OPT_USE_TILELANG_MHC_POST=False` (both appear in the A3 reference configs). ✅ Validated: error gone.
5. **`RuntimeError: Failed to build JIT module sgl_kernel_jit_dpsk_v4_hash_topk_act_sqrt_softplus_false`**
   — DSv4's fused hash top-k kernel (the model has `num_hash_layers=3`) cannot be JIT-built in this image.
   **Fix applied:** `SGLANG_OPT_USE_FUSED_HASH_TOPK=False` (also present in the A3 reference configs), plus
   `pip install ninja` as a build-tool belt-and-braces. ✅ Validated: `grep -c "Failed to build JIT"` = 0.
6. **Still no `/health=200`** in the last window (03:53:33 crash after the fixes above; that log's child
   exception was not captured before the session ended). Next session's first command:
   `grep -A25 "Scheduler hit an exception" /workspace/v4run/logs/server-v4fix3.log | tail -30`

5. **`aclnnCamMoeDispatchNormal failed … Failed to execute tiling function` with
   `[ERROR][CamMoeDispatchNormal] HCCL_BUFFSIZE is too SMALL … NEEDED_HCCL_BUFFSIZE=214MB, HCCL_BUFFSIZE=200MB`**
   DeepEP's MoE dispatch/combine window is smaller than the operator requires. The log states the exact
   requirement, so the fix is arithmetic, not guesswork.
   **Fix:** `HCCL_BUFFSIZE=1200` + `DEEPEP_HCCL_BUFFSIZE=2048` (the values used by the vendor-validated
   Ascend configs). ✅ Applied to the worker script; relaunch pending a fresh access token.

### Operational lesson: the jump token is single-session

The platform SSH token authorises roughly one live session. A `ControlMaster` session was established
successfully (all commands ran over it), but the supervising `expect` script had a 90 s timeout and exited,
which tore down the socket; the same token then returned `platform authorization denied` for every retry.
So: hold the master with `timeout` set to loop forever (`exp_continue`), never exit on idle, and use SSH
multiplexing for every subsequent command. Fix applied in `sessions/master.sh`.

## 2026-11-14 · Defect 7 and practice completion

**Defect 7 — DeepEP long-sequence capacity.** An 8k-prompt benchmark at c=8 killed the server:
`deep_ep.cpp:130 (num_tokens <= configured_capacity) num_tokens (16384) must not exceed the configured
capacity (8192)`. The default normal-mode dispatch capacity is 8192 tokens per round; 8k-token prefills
produce larger chunks. Fix (documented in the A3 reference configs, applied but **not yet re-verified**):
`DEEPEP_NORMAL_COMBINE_ENABLE_LONG_SEQ=1`, `DEEPEP_NORMAL_LONG_SEQ_PER_ROUND_TOKENS=2048`,
`DEEPEP_NORMAL_LONG_SEQ_ROUND=8`, plus `--chunked-prefill-size 8192`.

This also defines the **stability boundary measured on 4 dies**: short/2k prompts at c≤8 are stable;
8k prompts at c=8 exceed the DeepEP dispatch capacity. That is a configuration limit, not a hardware
limit, and it is the honest envelope for the numbers reported.

## 2026-11-14 · L3: NPU graph mode + tuned operating point

With the CANN custom-op path fixed, decode NPU-graph capture — previously fatal — now succeeds:

```
Capture target decode NPU graph begin. backend=full, num_tokens_per_req=1, bs=[1,2,4,8,16], avail mem=16.05 GB
Capture target decode NPU graph end. elapsed=13.25 s, mem usage=5.06 GB
```

**This retroactively explains defect #3**: the graph-capture crash was not a graph bug, it was the missing
`aclnnKvQuantSparseAttnSharedkvMetadata` op (aclnn ops are needed inside the capture), i.e. a symptom of
defect #2. Fixing the op path fixed graph mode.

Measured, graph vs eager:

| Cell | eager TPOT p50 | graph TPOT p50 | speedup | graph out tok/s | graph TTFT p50 |
| --- | --- | --- | --- | --- | --- |
| 128/512, c=1 | 57.1 ms | **19.58 ms** | 2.92× | 50.7 | 111.9 ms |
| 8192/1024, c=1 | 59.2 ms | **20.66 ms** | 2.87× | 46.1 | 1,214.3 ms |
| 2048/256, c=8 | 86.3 ms | **23.55 ms** | 3.66× | 178.9 | 731.7 ms |

Saturation (512/256, 64 prompts): c=16 → 360.8 tok/s @ 26.8 ms; c=32 → 482.5 tok/s @ 40.8 ms;
c=64 → **803.2 tok/s @ 65.3 ms**. Throughput still rising at c=64; with a TPOT p50 ≤ 50 ms SLO the tuned
operating point is c≈32 (≈480 tok/s), knee above c=32.

Against the vendor reference (V4-Flash, A3 ×8 cards = 16 dies, W8A8, graph, in 8k/out 1k, **TPOT 50 ms**):
ours is **20.66 ms on 4 dies** — target-class comparison, ≈2.4× faster per unit of silicon.

**L3 status:** graph mode validated ✅ · tuned operating point identified (c≈32) ✅ · envelope mapped to c≥64
and long-context decode flat ✅ · PD disaggregation ❌ scale-blocked (two pools / ≥8 dies required) —
documented rather than attempted. Remaining non-L3 work: accuracy evaluation, upstream PR push.
