### Long-context finding

TPOT is **flat with context**: 19.58 ms at 512 tokens → 20.66 ms at 8k. Long prompts cost TTFT
(111.9 ms at 128 tokens → 1,214 ms at 8k), not decode throughput — the hybrid CSA/HCA compressed KV
behaves as designed on this hardware.

## Stability boundary (measured)

Short/2k prompts at concurrency ≤ 8 are stable. An attempted **in 8192 / out 1024 / c=8** cell crashed the
server with a DeepEP dispatch-capacity assertion
(`num_tokens (16384) > configured_capacity (8192)`), i.e. the default long-sequence dispatch capacity for
normal mode. Config fix applied in launch config v7 (`DEEPEP_NORMAL_LONG_SEQ_*` + `--chunked-prefill-size 8192`),
not yet re-verified. Treat 8k-token prompts at high concurrency as **outside the validated envelope** of the
reported numbers.

## What each cell is for

| Cell | Workload | What it isolates | Typical failure of interpretation |
| --- | --- | --- | --- |
| `c1-decode` | in 128 / out 512, concurrency 1 | single-stream **TPOT** — the bandwidth floor of the hardware+model pair | taking it as "the speed of the model"; it is the *slowest* case by design |
| `c2-balanced` | in 2048 / out 256, concurrency 8 | the realistic chat serving point: TTFT and TPOT together | comparing against a different engine's batch-1 number |
| `c3-prefill` | in 16384 / out 128, concurrency 4 | **TTFT** under long prompts; prefill compute throughput | forgetting that TTFT here includes queueing behind 3 other long prompts |
| `c4-longctx` | in 32768 / out 256, concurrency 1 | KV-cache growth vs per-token decode cost | assuming the slowdown is compute; it is bandwidth reading the KV |
| `c5-openloop` | in 2048 / out 256, 2 req/s, open loop | queueing, tail latency, goodput under a realistic arrival process | reading p50 as the user experience; the p99 is what users complain about |

## How to read the table

1. **Decode is memory-bound.** TPOT at concurrency 1 ≈ `(active parameter bytes + KV bytes at that context) ÷
   effective HBM bandwidth`. If the measured TPOT is far below that floor, suspect a measurement problem
   (prefix-cache hit, too few output tokens, `--ignore-eos` mismatch) before celebrating.
2. **Throughput and latency trade.** A larger `--max-running-requests` raises output tok/s and raises p99.
   The useful operating point is before the knee, not at maximum throughput.
3. **TTFT is a prefill + queueing number.** The matrix flushes the prefix cache between cells, so these are
   cold-prompt numbers. A production chat workload with a shared system prompt will look better — that is
   RadixAttention doing its job, and it should be measured separately (same prompt prefix, cold vs warm).
4. **Goodput** counts only requests meeting both SLOs (default TTFT ≤ 2 s, TPOT ≤ 100 ms). When a
   configuration doubles throughput but halves SLO attainment, goodput says which one actually served users.
5. **Speculative decoding caveat.** EAGLE changes the *measured output token count* semantics slightly
   (draft tokens are verified, not delivered). Report it as configured, and keep it constant across the
   configurations you compare.

## Sanity bands (derived estimates, NOT measurements)

Derived from the branch implementation (`deepseek_v4_memory_pool.py` for the KV layout, `deepseek_v4.py` for
the model) and a roofline argument; they exist so a broken measurement is obvious. Do not cite them as
measured, and replace them with the real table as soon as one run exists.

**KV cache, per token (43 layers, hybrid CSA/HCA + index cache):**

| KV dtype | bytes/token | note |
| --- | --- | --- |
| FP8 packed (NPU default layout, if enabled) | ≈ 3,671 B | CSA 20×146 + HCA 20×4.56 + index 20×33 |
| BF16 (what this package launches with `--kv-cache-dtype bfloat16`) | ≈ 5,940 B | plus ≈ 3.2 MB/request for the 128-token SWA windows |

Cross-check: the compressed-KV-only figure is ≈ 7.7% of DeepSeek-V3.2's per-token KV, which matches the
model report's "7% of KV" claim — a useful signal that the derivation is sane.

**Concurrency ceiling** (with weights resident and a 0.85 memory fraction; KV replicated per attention-TP
group, multiplied by DP-attention):

| Slice | weights | KV budget | 32k-context requests | 1M-context requests |
| --- | --- | --- | --- | --- |
| 512 GB node, W8A8 (A2/A3 8 dies) | 283.9 GB | 151 GB | ~164 (×8 with DP-attn) | ~5.3 (×8) |
| 512 GB node, native FP4+FP8 (950 only) | 159.6 GB | 275.6 GB | ~300 (×8) | ~9.6 (×8) |
| 256 GB slice (4 dies) | W8A8 300.1 GB | **does not fit** | — | — |

The last row is the whole feasibility story: on a 4-die 256 GB slice the W8A8 weights alone exceed the
budget; only a 950-class slice with ≥ ~96 GB/die can host this checkpoint on 4 dies.

**TPOT floor and realistic band** (decode is memory-bound; floor = bytes read per step ÷ effective bandwidth):

| Hardware | roofline floor (c1) | realistic c1 TPOT including EP communication |
| --- | --- | --- |
| 950PR/DT (2–4 TB/s per device, 60–75% efficiency) | 0.5–2.05 ms | ≈ 6–12 ms |
| A2 (≈1.5 TB/s per device) | 1.86–3.72 ms | ≈ 12–25 ms |

The gap between floor and realistic band is the MoE all-to-all (on the order of 86 HCCL collectives of
~130 µs per decode step at EP8). If a measured c1 TPOT is *better* than the floor, the measurement is wrong
(cache hit, too few output tokens, wrong model); if it is several times the realistic band, look at
`--disable-cuda-graph` coverage, `--mem-fraction-static`, and HCCL socket settings.
